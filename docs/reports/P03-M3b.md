## The evaluation

OpenMLS 0.9.2 with its RustCrypto provider resolves to 194 crates, about 109 new to the tree:
RustCrypto and libcrux (two more cryptography stacks), `bindgen` and `clang-sys` at build time,
`rayon`. Clients must validate KeyPackages fully under RFC 9420 either way, so the server's checks
are defence in depth plus one thing only the server can enforce: that a package names the device
that uploads it. A focused parser does that with no new crate. The owner chose it.

## What was built

1. **KeyPackage checks** (`crates/keys/src/mls.rs`): RFC 9420 encoding, strictly; mls10;
   ciphersuites `0x0001`/`0x0003`; honest X25519 keys (init ≠ encryption) and Ed25519 signature
   key; a basic credential whose identity is the uploading device's ID; capabilities; a current,
   bounded lifetime; both `SignWithLabel` signatures; `last_resort` from the package itself;
   `KeyPackageRef`. An encoder for clients and tests.
2. **Proven against OpenMLS** (`tools/openmls-vectors`, outside the workspace): OpenMLS's
   X25519/Ed25519 packages pass with OpenMLS's own `KeyPackageRef`; its last-resort package is
   recognised; its P-256 package is refused; every single flipped byte of a package is refused.
3. **Wire formats** (`crates/proto/src/keys.rs`, PROTOCOL.md §4.5): upload and fetch answer;
   system notice kind 3, `KeyPackagesLow`.
4. **Registry**: table `mlskp` under (device, `KeyPackageRef`) with expiry; the last-resort
   package on the device row; claims that delete exactly one record (as M3's prekeys); expired
   packages never served; deletion with the account; the worker sweeps expired packages.
5. **`api`**: `PUT /v1/keypackages` (authenticated before the body; checked off the runtime),
   `GET /v1/keypackages`, `POST /v1/keypackages/fetch` with M3's throttles (separate records),
   per-target budget and last-resort fall-back, and refill notices.
6. Docs: PROTOCOL.md §4.5; threat model §1 (one row, approved by the owner on 2026-11-15) and §3.11; D-0051; the
   plan; fuzz target `keypackages`.

## Security review

`security-review` over the diff (an independent reviewer, read-only): **no finding at or above
the reporting bar.** It checked the parser against RFC 9420 §7.2 and §10 field by field, the
exact boundaries of both signed regions (`LeafNodeTBS` for a `key_package` source ends after the
leaf's extensions; `KeyPackageTBS` covers everything but the two signatures, so no field escapes
signature coverage), minimal varints, the credential-type and identity-length checks, device
binding, last-resort handling (decided by the signed extension, stored only on the uploader's own
device row), double-serving and expiry, injection and authorization. Fixed from its notes below
the bar: the varint encoder now writes every RFC 9420 size class (it was correct only for the
lengths current limits produce), with a round-trip test. Recorded, not changed: the MLS signature
key is not tied to the device identity key on the server (only the authenticated device can
upload; clients validate fully); expired, unswept packages count toward a device's quota until the
sweep; a package marking `last_resort` only in its leaf is stored as single use (harmless).

## Open risks

- Only X25519/Ed25519 ciphersuites are accepted until Prompt 5 decides on a post-quantum one
  (issue #24); the allow-list is one constant.
- The server's checks are a strict subset of RFC 9420's; clients must validate fully.
- The local podman VM ran out of memory during this milestone (Iggy, 2.3 GB of 3.8 GB, in an OOM
  restart loop; issue #31 is the likely cause); see "Run on the Mac".
