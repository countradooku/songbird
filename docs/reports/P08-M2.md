# P08-M2 — Numbers and outages

- Date: 2026-11-18
- Plan: [P08-plan.md](P08-plan.md) (D-0094); decision D-0096
- Status: built and tested.

## Setup

Apple M5 Pro (18 cores, 48 GiB), macOS 27.2.1; compose SurrealDB v4.0.1 and valkey-jobs under
podman; release build; mock APNs and FCM over TLS 1.3 and HTTP/2 on loopback (4 connections per
provider); consumer batch 256, concurrency 256. `services/push/tests/outage_live.rs`.

## Numbers

| Measure | Result |
| --- | --- |
| Burst of 20,000 wake-ups (`m2_numbers`, 5 runs) | **9,800 to 28,600 pushes/s**; bound by the token lookup in SurrealDB (one per job), whose speed varied with the local server's load |
| Same burst, enqueue→provider | p50 0.27 to 0.75 s, p99 0.51 to 1.5 s: the burst queueing behind itself |
| Steady 1,000 wake-ups/s (2 runs) | **p50 1.3 to 1.9 ms, p99 6.5 to 11 ms**, max 26 to 37 ms |
| Before the reader fix | ~850 pushes/s (see below) |

## A flaw found and fixed

The first run gave ~850 pushes/s while every part alone was fast (queue ~38,000 jobs/s, APNs
client ~38,000 sends/s). The job queue used **one reader connection** for every stream, and
Valkey runs a connection's commands in order: the ring consumer's 250 ms blocking read on an empty
`j:ring` held every `j:push` read behind it. The worker had the same flaw since D-0036 (cleanup
reads behind deletion reads). One reader connection per stream now: the consume loop went from
~800 to ~34,000 jobs/s with no provider.

## Outages (all pass, `-j 1`)

| Scenario | Result |
| --- | --- |
| FCM answers 503 to everything for 3 s | 67 requests refused (the breaker kept it cheap); **all 200 devices woken 2.0 s after recovery**; nothing dead-lettered |
| APNs black-holed (accepts, never answers), 300 ms timeout | breaker opens (at most one probe per cooldown); all 100 devices woken after recovery |
| FCM rate-limits with `retry-after: 1` | the retry waits ≥ 0.95 s, then delivers |
| `push` crashes mid-burst (runtime dropped with jobs in hand) | a new instance reclaims after the visibility timeout: all 300 devices woken, 64 twice, nothing lost |
| APNs down while a phone is offline (end to end) | the three messages wait in the mailbox, the wake-up goes out once APNs is back, the phone reads them in order (`gate_m5`) |
