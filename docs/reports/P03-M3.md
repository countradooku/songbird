## What was built

1. **XEdDSA** (`crates/keys/src/xeddsa.rs`), from libsignal's specification and code, not
   linked: verification, an honest-key check for X25519 public keys, and a signer for clients
   and tests. Byte-identical to libsignal both ways; stricter in requiring a canonical `s`.
2. **ML-KEM-1024 key checks** (`crates/keys/src/kem.rs`): libsignal's `0x0A` serialization and
   FIPS 203's modulus check, which **aws-lc-rs 1.19 does not apply on its own** (found while
   building; a test asserts it).
3. **Wire formats** (`crates/proto/src/keys.rs`, PROTOCOL.md §4.4): the upload and the fetch
   answer, strict and bounded; stored forms of each key; system notice kind 2, `PrekeysLow`.
4. **Registry** (`crates/accounts`): identity key (once), signed and last-resort prekeys per
   device; tables `otpk` and `otkem`; uploads in one transaction (identity never replaced, at
   most 200 of each kind, duplicates refused, first upload complete); claims that hand each
   one-time key to exactly one fetch; deletion of an account's prekeys. Our own `THROW`s now
   carry a tag (`songbird:<tag>`) the database layer passes through, so a transaction's refusal
   says which rule refused it.
5. **`api` endpoints** (`services/api/src/keys.rs`): `PUT /v1/keys` (authenticated from the
   headers before the up to 169 KB body is read; every key and signature checked off the async
   runtime), `GET /v1/keys`, `POST /v1/keys/fetch` with per-requester and per-range throttles
   and a per-target one-time budget that falls back to last-resort keys instead of refusing.
6. **Refill notices**: a device left below 10 one-time keys gets a `PrekeysLow` system notice,
   signed by the system key, through the send path `api` links (`Submit::system`), at most once
   an hour.
7. Docs: PROTOCOL.md §4.4 and the XEdDSA vector; threat model §1 (two rows, approved by the owner on 2026-11-15)
   and §3.10; runbook "Key directory: fetches failing or devices out of prekeys"; D-0050; the
   plan's M3 and new M3b rows; `config/dev/api.toml`; fuzz target `prekeys`.

## Security review

`security-review` over the diff (an independent reviewer, read-only): **no finding at or above
the reporting bar.** It checked key substitution (the identity key compared before and inside the
transaction; every signed key verified over its full serialization; uploads only for the
authenticated device), authorization (counts for one's own device; fetches only within the
target account, disabled devices excluded, the requester's own skipped), the cryptography
(XEdDSA's sign bit, canonical `s`, the challenge over the signature's `A`, the byte comparison
with `R`; the honest-key check; the modulus check's decoding of `t`), double-serving, SurrealQL
injection (constant fragments, bound values) and the decoders. Of its notes below the bar, two
were trivial to close and are fixed:

- The `THROW` tag was read from any failed statement's message; it is now read only from
  statements that threw, so no other error message can be misclassified.
- A fetch whose stored row failed to parse answered 404 after its keys were claimed; such a
  row is now skipped and the other devices' bundles are served.

Recorded, not changed: one fetch spends one unit of the target's one-time budget for all of the
target's devices (at most six, M4's limit), so the drain rate scales with the device count
(excluded as DoS; the budget is per account by design); the exactly-once guarantee rests on
SurrealDB raising write conflicts for concurrent deletes of one record, so a change of storage
engine re-runs the gate; 404 against 200 tells whether a random 128-bit account ID exists, which
a key directory cannot avoid.

## Open risks

- Sessions started once a target's one-time budget is spent use the last-resort ML-KEM key and
  no one-time X25519 key: PQXDH's defined degraded mode, replayable until the recipient rotates
  its last-resort key. The budget trades this against availability.
- The device identity key is bound to the device by first upload only until M4's signed device
  list makes the account identity key vouch for it.
- A client stack must speak ML-KEM-1024 (owner's decision); libsignal's default is still
  Kyber1024.
- One fetch spends one unit of the target's one-time budget for all its devices (at most six).
- The exactly-once guarantee rests on SurrealDB's write-conflict detection for concurrent deletes;
  any change of storage engine (TiKV later, per the locked stack) re-runs the gate test.
