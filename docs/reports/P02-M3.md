## What was built

- **`crates/runtime`** (D-0032): one pinned OS thread per worker core, each with its own
  current-thread Tokio runtime; one listener per core with `SO_REUSEPORT`. Pinning through
  `rustix` (already in the graph); no new crates. `[delivery.runtime]`: `workers`, `pin`,
  `backlog`, `storage_threads`.
- **Storage runtime**: the mailbox runs on its own multi-thread runtime, one thread per Iggy
  partition by default.
- **Device directory on `papaya`**, chosen by benchmark against scc, dashmap and the old
  `Mutex<HashMap>` (`bench/directory`). Routing sends under the map's guard without cloning.
- **Cross-core inboxes**: tokio mpsc kept, chosen by benchmark against kanal and crossbeam.
- **Per-core metrics** (`songbird_telemetry::sharded`): one shard per core on its own cache line,
  summed at scrape.
- **Allocation gate**: a test-only counting allocator (`crates/alloc-count`, the one recorded
  `unsafe` exception, D-0033, run under Miri in the deep tier) and the CI test above.
- **Mailbox under load**: Iggy's backpressure (`TransientNotAccepted`) is retried after 1 ms (doubling
  to 64 ms), not on the slow schedule for broken connections; at saturation that schedule cut a
  node from 270,000 to 6,000 messages/s.
- **compio benchmark** (`bench/runtime-echo`, D-0028): not adopted, below.

## Scaling

`bench`: `target/m3/scale.sh` (load generator `run`, 2,000 devices, 8 s per run). "Max" offers
1,000,000 messages/s and reports what gets through; latency at a fixed 50,000/s.

### Delivery path isolated (in-memory mailbox)

| Cores | Max messages/s | p50 / p99 at 50,000/s |
| --- | --- | --- |
| 1 | 70,554 | 1.3 / 5.6 ms |
| 2 | 139,551 | 0.45 / 1.0 ms |
| 4 | 375,243 | 0.19 / 0.57 ms |
| 8 | 625,698 | 0.11 / 0.35 ms |

At 8 cores each core is about 70 % busy; the in-memory mailbox's single lock and the kernel's
loopback work (25 % system time, 16 % softirq machine-wide) are the limits, not the cores.

### Production mailbox (Iggy on tmpfs, 4 partitions)

| Cores | Max messages/s | p50 / p99 at 50,000/s |
| --- | --- | --- |
| 1 | 62,961 | (saturated) |
| 2 | 122,482 | 0.58 / 1.3 ms |
| 4 | 231,847 | 0.39 / 0.88 ms |
| 6 | 285,059 | 0.38 / 0.71 ms |

Before the storage runtime the same setup gave 65,600, 127,900, 215,600 and then 165,100 with 8
cores (the four partition writers shared the main thread). At 6 cores now: delivery cores about
60 % busy, storage threads about 30 %, Iggy's shards 15–20 %. Nothing saturates, so the number is set by the
closed-loop latency of 2,000 devices and a load generator sharing the machine; with 10,000
devices the load generator itself (8 logical CPUs) becomes the limit (187,000–239,000/s). The
curve on the reference hardware, with separate load machines, belongs to Prompt 13. On this
disk (btrfs) every store is fsync-bound far below these numbers (D-0031).

## Allocations per message

`tests/e2e/tests/allocations.rs` runs the server on its own thread and counts that thread's heap
allocations while a sender and a receiver exchange 2,000 messages one at a time (decode, check,
store, route, write, ACK). valgrind DHAT attributed each site:

| Site | Per message | Status |
| --- | --- | --- |
| Recipient list collected for the duplicate and device-list checks | 1 | removed: a reused per-session buffer |
| Accounts addressed (directory check) | 1 | removed: inline set of 8 |
| Decoded recipient list (`frame.rs`) | 1 | kept: the frame is decoded into owned envelopes |
| Store request handed to the mailbox | 1 | kept: crosses to the storage runtime |
| In-memory mailbox: recipient list and idempotency record | 2 | development backend only |
| `seq` list returned by the mailbox | 1 | kept: the result crosses back |
| Route, socket write, ACK | 0 | — |

7.20 → 5.20 allocations (894 → 798 bytes) per message.

## Runtime: per-core Tokio against compio (D-0028)

Same sockudo-ws echo server on both, 512 connections, 4 messages in flight each, two rounds:

| Cores | Tokio (epoll) | compio (io_uring) |
| --- | --- | --- |
| 1 | 176,427–177,563 round trips/s, p99 11.6 ms | 180,275–180,376, p99 11.5 ms |
| 4 | 716,713–718,104, p99 3.7–4.1 ms | 744,867–747,999, p99 3.4–4.0 ms |

compio is 2–4 % faster. Recommended: stay on per-core Tokio (the locked stack). Against compio:
it would put io_uring on the internet-facing service (a large kernel attack surface with a long
record of privilege-escalation bugs, and the seccomp relaxation the Iggy container already
needs); the Iggy SDK is Tokio-only, so every core would run two runtimes; compio is pre-1.0 with
breaking minor releases. io_uring against epoll is measured again in M7.

## Device directory and inboxes

Numbers in D-0032. papaya: 362.6 M operations/s with p99 211 ns at 16 threads (scc 134.9 M,
dashmap 127.9 M; the old `Mutex<HashMap>` 4.8 M with p99 30.6 µs). Inboxes: tokio mpsc and
crossbeam with a `Notify` within noise of each other (p99 6–22 µs at 2 M messages/s over 8
cores); kanal had millisecond tails.

## Memory per idle connection

10,000 idle authenticated connections on 4 cores: resident memory grew from 53 MiB to 301 MiB,
about **26 KiB per connection** (4 KiB read and 4 KiB write buffers, the session task, its two
inbox channels, allocator caches). Follow-up below: release buffers on idle connections.

## Bugs found and fixed

- **Iggy backpressure retried on the broken-connection schedule** (20 ms doubling to 1 s): a
  saturated node fell from about 270,000 to 6,000 messages/s. Now 1 ms doubling to 64 ms.
- **The mailbox's writers shared the main thread**: throughput fell when cores were added (216,000
  on 4 cores, 165,000 on 8). Now a storage runtime.
- **Dropping the storage runtime on an error path panicked** (a runtime dropped inside another
  runtime's context). It is now always shut down in the background.
- **Invariant 6 caught a log field**: the new start-up log named a field `pin` (CPU pinning),
  which the redaction filter treats as sensitive (a PIN); the smoke test failed and the field is
  now `pinned`.
- Local tooling, recorded for reruns: each benchmark run's Iggy stream filled the tmpfs quota after
  a few runs; the script now restarts Iggy clean per run.

## Open risks and follow-ups

1. **26 KiB per idle connection**: allocate read and write buffers lazily and release them when a
   connection goes idle (master prompt §4); measure again.
2. **Single-machine numbers**: the load generator, Iggy and `delivery` share 16 cores; the curve
   past 6 cores needs separate load machines (Prompt 13).
3. **Writer pipelining** (sealing the next batch while one appends): not needed at these rates
   (storage threads about 30 % busy); revisit in M7 with the reference hardware.
4. **`songbird-telemetry`'s redaction tests are order-dependent** when run in one process
   (tracing's global callsite registry): they fail under a plain `cargo test -p
   songbird-telemetry`; `cargo xtask ci fast` is unaffected. Fix by running them in separate
   processes.
5. Kernel profiling (call stacks, system time) needs `perf_event_paranoid` ≤ 1 on the
   measurement machine.
