## Changes from the plan

- Each vault incarnation has a random **epoch** in its objects' prefix, and turning a vault off
  deletes its rows at once, leaving a `vault_gone` row for the worker. The first version marked
  the row "deleting", which kept the same recovery key from opening a new vault until the worker
  ran, and would have let the worker's prefix deletion reach a new vault's objects.
- Chunk listing is `GET /v1/vault/chunks?after=` (no body) instead of a `POST`.
- Chunks are buffered in `api` (at most 8.25 MiB each) rather than streamed into RustFS: a chunk
  is one S3 `PutObject`, and the body must be signed and checked before it is stored.
- The vault's access hash context lives in `songbird-proto` (no crypto there); `api` and the
  format each compute the hash, so `api` links no backup crate.

## Threat-model rows for the owner

§1: backup vaults (the owner, counts, generation, no times); the vault's keyed throttle
records; turned-off vaults awaiting deletion. §3.27: probing, writes by others, linking a vault
to its key, filling the service, racing writers, vaults outliving accounts, size over time. All
marked awaiting the owner's approval in `docs/THREAT_MODEL.md`.
