## What was built

1. **The contact gate in the send path** (`crates/send`, PROTOCOL §5.10):
   - every send to another account is classified from the directory snapshot alone: sync,
     direct, broadcast, request, group or sealed;
   - a closed account takes a send only with its access key (constant-time compare) or as a
     franked request to that one account;
   - otherwise reason 10 (access required) or 11 (invalid request);
   - no store round trip, and no allocation for 1:1 sends.
2. **The directory snapshot** gains each account's access key, open flag and request policy. A
   profile or policy change bumps its version, so every node follows. Static development
   directories treat accounts as open.
3. **The gate** (`songbird_send::gate`):
   - request budgets per sender, per (sender, recipient) and per recipient, and broadcast
     accounts per sender, in `valkey-hot` under keyed names. A cost-weighted GCRA, shared by every
     node and both transports, failing closed;
   - then the request policy and the block row;
   - blocked and refused requests are accepted and stored nowhere, with the budgets spent first,
     so a block cannot be told from the answers;
   - `MemoryGate` gives the same rules in tests.
4. **Blocking and the request policy** (`crates/accounts/src/blocks.rs`,
   `services/api/src/requests.rs`):
   - `PUT`/`DELETE /v1/blocks`, `GET`/`PUT /v1/account/requests`;
   - rows are keyed hashes of the pair with a keyed owner tag and a per-owner counter (at most
     1,000, held under concurrency);
   - tightening from any listed device, loosening from the primary only (D-0058).
5. **Per-class rate limits:**
   - group sends (shared bodies) have their own per-device budget within the existing one, on
     both transports;
   - requests and broadcasts are budgeted per account across the cluster;
   - channels wait for Prompt 5.
6. **Broadcast lists:** per-device envelopes to up to 256 accounts (configurable), each a contact
   (one XOR of their keys) or open, within an hourly account budget.
7. **GDPR:**
   - the worker deletes an account's block rows by its owner tag and verifies none are left;
   - the export reports the request policy and the block count;
   - the policy flag goes with the account row.
8. **Configuration:** `[api.requests]`, `[delivery.requests]` (secret, `valkey-hot`, budgets),
   the worker's `requests_secret` and the group-send limits; required in staging and
   production.
9. **The test client** (`songbird-client::send_hinted`) sends with hints and resends them after
   a restore.
10. Docs:
    - PROTOCOL.md §5.10 and §5.11;
    - threat model §1 (three rows, awaiting approval), §3.20, §4 (server-enforced settings) and
      §6;
    - D-0062.

## Open risks

- **Timing.** Fixed with D-0064: a dropped send now takes a durable store too.
- **Sybil recipients.** Sybil accounts can use up a recipient's request budget for an hour.
  Contacts are unaffected.
- **Directory snapshots.** Every node now holds every account's access key in memory, and
  reloads on profile changes. An incremental reload is Prompt 13's.
- **Fixed after the security review (D-0064):** shared bodies no longer bypass the gate (they
  need every closed member's key until Prompt 5); a dropped send no longer shows through
  idempotency; only the primary opens an account, and blocks apply to open accounts. Ephemeral
  frames from strangers stay ungated (encrypted, limited per connection).
- **Client rules:** blocking must rotate the profile key, and every app must publish a profile
  at registration. Apps are not written yet; PROTOCOL states both.
