## What was built

1. **The report format** (`crates/proto/src/report.rs`, PROTOCOL §5.14): the stamp the app kept,
   the claimed sender, the franking key and the content exactly as received. It is bounded
   (content of 1 to 61,440 bytes), strict and fuzzed.
2. **`POST /v1/reports`** (`services/api/src/reports.rs`), from a listed device. The checks, in
   order:
   - the reporter's budget, spent first;
   - the franking key (current or previous);
   - the 30-day window;
   - the stamp, which binds the sender (attested, or none for a sealed send) and the recipient
     (this reporter, or none for a group's shared body);
   - the commitment, which must open to the content, in constant time.

   The verification is a pure function with known-answer tests.
3. **The minimal report**:
   - its fields: reason, sender, whether attested, direct or group, the stamp time, the report
     time and the content;
   - **sealed to an offline moderation key** (X25519, HKDF-SHA256 under `songbird.v1/report`,
     AES-256-GCM): the provisioning seal, generalized with a domain label, so one reviewed
     construction serves both;
   - **no reporter, and nothing else about the conversation**.
4. **The queue** (`crates/accounts/src/reports.rs`):
   - rows are named by a keyed hash of the stamp's tag, so each message is reported once;
   - they are kept 30 days (at most 90), swept by the worker, and deletable by moderators.
5. **`songbird-admin reports`**:
   - `keygen` writes the private key with mode 0600 and prints the public key for the config;
   - `list`;
   - `open` decrypts and decodes the content, showing its kind and text;
   - `delete` needs `--confirm` and is audit-logged.
6. **Configuration**: `[api.reports]`, required in staging and production, and needing
   `[api.requests]` and the franking key.
7. Docs:
   - PROTOCOL.md §5.14;
   - threat model §1 (two rows, awaiting approval), §3.21 and §6;
   - D-0063;
   - fuzz target `franking` now also covers reports.

## Open risks

- `api` sees a reported message's content in memory while verifying (never decoded, never stored
  unsealed).
- **Sealed senders** can only be claimed in a report, not attested.
- **The moderation key** must stay offline; whoever holds it reads every queued report. Rotation
  is a configuration change, and reports already sealed need the old key.
- **No moderation workflow** (actions on reported accounts) is built yet: that is Prompt 11's
  (abuse prevention). The queue is ready for it.
