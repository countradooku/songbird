## What was built

- **Backups (`songbird-admin backup run`):**
  - SurrealDB `GET /export` is streamed into `age`. The plaintext never touches disk.
  - Encrypted to two recipients: the owner's offline identity and the verification identity.
  - A SHA-256 checksum the server verifies.
  - Stored write-once: S3 Object Lock in compliance mode, retention by tier (5-minute exports 25 h, first of the day 8 d, of the week 29 d, of the month 93 d).
  - The timer's database user has the `VIEWER` role (export only).
- **Restore and verification (`backup restore | verify`):**
  - The backup is decrypted in memory and imported, **only into an empty database**.
  - Consistency checks: counts, devices without an account, the store generation.
  - A restore bumps the store generation.
- **Restores trust the server, not the uploader.** This was found while writing the threat model:
  - Age recipients are public keys, and the put-only key can write over an older backup's name.
  - On a versioned bucket that write makes a new current version, so a plain GET would restore a forgery that adds devices of the attacker's choosing.
  - Restores now read the **first stored version** of each name, chosen by the server's `LastModified`.
  - A name written twice, or a backup named for another time than it was stored at, fails verification and is never restored.
  - `--before <time>` restores from before a compromise.
  - The S3 client gained `ListObjectVersions` and GET by version ID.
- **Deletion journal (D-0041):** a restore no longer brings deleted accounts back.
  - Before deleting anything, the worker puts an empty, write-once tombstone in the backup bucket,
    named by HMAC-SHA256(journal key, account ID): no account ID, locked 93 days. Its credential
    can only put under `deletions/`; a deployed worker without the journal is refused at startup.
  - `backup restore` checks the journal key before touching anything, then re-deletes (through
    the outbox, so the worker clears every store) every restored account with a tombstone.
    `--no-journal` is explicit and audit-logged; `--before` applies to tombstones too.
- **Safety in `songbird-admin`:** restore, generation bump and accounts import need `--confirm <namespace>/<database>`. They write an append-only, fsynced audit log before and after the action, and refuse to run if the log cannot be written (master prompt §7).
- **Store generation and client resend** (PROTOCOL.md §3.6):
  - The generation lives in the registry (`store:g`) and delivery follows it.
  - Clients keep a bounded send log (100,000 messages, 30 days).
  - On a larger generation, a client resends everything without an end-to-end receipt, with the original idempotency keys. A surviving mailbox replays them; a lost one stores them again.
  - **Bug found by the drill and fixed:** a receipt that reached the sender's client before its own `SendResult` was lost, so that entry stayed in the log for good and was resent after every restore (11,576 spurious repeats in the first gate run, 0 after). Such receipts are now remembered in a bounded set.
- **Load generator `--scenario restore`:**
  - The checker allows what a restore legitimately causes: numbering restarts, and repeats are dropped by message ID. It never allows a loss.
  - Options `--offline-recipients` and `--no-resend`.
  - `songbird-admin accounts import` loads a static directory into the registry for drills.
- **Off-site, in OpenTofu (`deploy/tofu/envs/backups`, `deploy/bin/backups-up`):**
  - An **owner-only root**: its own state at the other provider, an Organization-level key, not the deploy pipeline's.
  - A dedicated Scaleway project; a versioned bucket with compliance-mode Object Lock (`prevent_destroy`, no `force_destroy`).
  - Expiry per tier, one day after its lock.
  - A **writer** limited to `PutObject`/`PutObjectRetention` under `registry/`; a **verifier** limited to reading. The IAM permission sets are narrowed by the bucket policy, because `ObjectStorageObjectsWrite` alone would also allow ACL and lock-configuration changes.
  - A `tofu test` asserts all of this; a widened writer fails it.
- **Deployment (Ansible):**
  - The `backup` role on the data host:
    - creates the VIEWER user and pulls the admin image;
    - installs a 5-minute systemd timer that runs `songbird-admin` in a read-only, unprivileged container;
    - runs one backup during the deploy, so a failure fails the deploy;
    - fails an environment without a configured bucket (staging excepted).
  - **Verification on a host in an environment of its own:**
    - the topology role `verify`, which the topology module refuses beside production roles;
    - `backup-verify.yml`, run by the owner;
    - every day: restore into a throwaway in-memory SurrealDB on loopback, check, and fail if the newest backup is older than 1 hour.
  - Its identity and read key are in an owner-only SOPS file (`sops-config`). The environment's CI-readable file holds only the put-only key.
  - The `songbird-admin` image adds age 1.3.2, pinned by SHA-256, and joins the release matrix.

## Open risks

1. **Off-site path not exercised.** There is no Scaleway account yet (the owner has only a Hetzner VPS; D-0041 keeps the backups at a different company from production). Not yet confirmed against Scaleway:
   - Object Lock enforcement;
   - the writers' put-only limits, including a PUT that carries `x-amz-acl`;
   - checksum and retention headers.
   The runbook's setup step 8 checks each of these once at setup.
2. **Deletions in the outbox relay's window.** A deletion whose job had not reached the worker when the registry was lost (sub-second) has no tombstone and is lost with the registry. The user sees their deletion request undone and can repeat it.
3. **Deleted accounts stay in encrypted backups for up to 93 days** (approved, D-0041). They are unreadable from production and are deleted again by any restore.
4. **No alerting yet.** A stopped backup timer is caught by the daily verification (newest older than 1 h), so the RPO can silently grow to a day until the observability work adds alerts. The verification writes a Prometheus text sample ready for it.
5. **Backups and tombstones stored after a compromise are untrusted.** Restore with `--before`. Overwrites of older backups are detected and ignored.
6. **The 2-hour RTO is not drilled end to end** (rebuild at the second provider plus restore). The software restore takes about 1 minute per million accounts.
7. **Deployment templates** for the services' own configuration sections (the worker's included) are not written yet; the configuration validation refuses a deployed worker without the journal meanwhile.
8. **Clients other than the Rust client** must implement the send log and the generation check (PROTOCOL.md §3.6) until Prompt 4's delivery receipts.
