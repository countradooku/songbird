## The evaluation the prompt asks for

| | libsignal `zkcredential` / `zkgroup` | **RFC 9497 POPRF (chosen)** | Plain linkage in a stricter store |
| --- | --- | --- | --- |
| Payment unlinkable from the account | Yes | Yes | No: a breach or subpoena of billing names who pays |
| Licence | AGPL-3.0-only: never linked (D-0047); a port like D-0049's | Our code, from an RFC | — |
| What has to be owned | Keyed-verification credentials with hidden attributes, their proofs, blind issuance | One PRF, one DLEQ proof (≈ 500 lines), RFC test vectors | Nothing new |
| Metadata (level, month) | Public attributes | The POPRF's public input, bound by the proof | Columns |
| Tagging a user with their own key | Needs key consistency | Needs key consistency: one long-lived key per ID, pinned in the app | — |
| Needed for | Credentials bound to a value the issuer must not see (Signal's backup IDs) | Payments: "someone paid for Plus for December" | — |

Hidden attributes are not needed for payments, so the smaller primitive wins. The POPRF (rather
than the plan's first idea, a VOPRF key per level and month) keeps **one** public key per ID that
apps can pin, with the level and month bound by the proof: a server cannot hand one user a
month key of their own.

## Changes from the plan

- **POPRF instead of a key per (level, month).** One key pair per key ID; the metadata is the
  POPRF's public input. Same unlinkability, one pinned key, and the proof binds the metadata.
- **3 days of grace** after a token's month (a store's renewal retry).
- A month's token is redeemable in that month and the one before.
- The token secret is shared by `api` and billing only; key rotation adds an ID.
