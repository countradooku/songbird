## What was built

1. **Wire formats** (`crates/proto/src/devices.rs`, PROTOCOL.md §4.6), strict and bounded:
   - the signed device list: at most 16 entries, exactly one primary, no device twice, signed by
     the account identity key over a domain-separated body, versions only growing;
   - the link request;
   - the provisioning plaintext.
2. **Provisioning crypto** (`crates/keys/src/provisioning.rs`), for clients and tests; the server
   never runs it:
   - the new device's X25519 key for the QR code;
   - sealing (fresh ephemeral X25519, HKDF-SHA256, AES-256-GCM; honest keys only);
   - the link confirmation tag (HMAC-SHA256 under a key that travels only inside the sealed
     message).
3. **The provisioning channel** (`services/api/src/devices.rs`):
   - a 128-bit bearer ID under a keyed hash in `valkey-hot`;
   - one message of at most 4 KiB, written once and read once (long poll up to 25 s);
   - ten minutes, then gone;
   - opening and reading are unsigned and throttled per IP range.
4. **Linking**:
   - the primary's single-use link token: 256-bit, hash stored, ten minutes. It reserves a
     server-chosen device ID and counts toward the limit while outstanding.
   - the new device's link request: both keys proven (Ed25519 and XEdDSA) over a transcript
     binding the token, the device ID and the server, plus the confirmation tag;
   - the identity key is fixed at link time.
5. **Pending devices**: a linked device authenticates at once but is outside the send check
   (`Directory::with_pending`), and key and KeyPackage fetches skip it, until a signed list names
   it. The primary checks the confirmation tag first. The server saw the token but never the
   confirmation key, so it cannot link keys of its own unnoticed.
6. **The signed device list** (`PUT /v1/devices/list`, `POST /v1/devices/list/fetch`). Accepted
   only if it verifies under the account identity key, names the requester's account, is within
   the limit, has a higher version, and every entry matches an enabled device's stored keys with
   the right primary flag. Devices it leaves out are disabled in the same transaction.
7. **Removal**:
   - by a list, or a linked device removing itself (`DELETE /v1/devices/self`); never the
     primary;
   - a `DeleteDevices` outbox job; the worker deletes the devices' mailbox, push registrations,
     upload grants and objects, rows, prekeys and KeyPackages, and verifies, as account deletion
     does;
   - the account's other devices are untouched.
8. **Device limit** (primary + 5) under races: every change to an account's devices writes the
   account row in its transaction, so concurrent changes conflict and retry.
9. **Notices**: `DeviceListChanged` (kind 1, signed by the system key) to the account's other
   devices on link, list and removal.
10. Docs and operations:
    - PROTOCOL.md §4.6;
    - threat model §1 (four rows, awaiting approval), §3.12 and open risks;
    - D-0052, the plan's M4 and M4b rows, the runbook section "Devices";
    - `[api.keys.devices]` settings;
    - fuzz target `devices`, added to the nightly matrix.

## Security review

`security-review` over the diff (an independent reviewer, read-only): **one finding at the bar,
fixed.**

**The finding.** Before M4 every account had one device, so `DELETE /v1/account`, the username
endpoints and invites never asked which device called. M4's linked devices authenticate as soon
as they link. A device linked by phishing a QR scan, or a stolen linked device, could therefore
delete the account irreversibly (the deletion journal keeps it gone across a restore) before the
primary removed it. Fixed:

- only the primary deletes the account, checked inside the deletion's transaction
  (`begin_account_deletion_by`);
- a pending device is refused every account-wide change (usernames, the username key and link,
  invites);
- tested (`a_pending_device_changes_nothing_account_wide_and_only_the_primary_deletes`);
- recorded in D-0052, PROTOCOL.md §4.6 and threat model §3.12.

**Notes below the bar, fixed:**

- The directory loaded devices and pending flags in two queries. A device removed in between
  could briefly be a recipient. It is now one snapshot (`load_directory_full`).
- A first device without the primary flag (none exist; pre-M4 development data only) could have
  removed itself. Removal now requires the flag to be explicitly false.
- Device deletion now re-checks that upload objects are gone, as account deletion does.
- Lists of an account being deleted are no longer served.

**Notes recorded, not changed:**

- A self-removed device stays in the stored signed list until the primary signs a new one. The
  server cannot re-sign it; the device is disabled and deleted everywhere else.
- A one-time-prekey upload that passed authentication just before its device was disabled could
  leave orphan prekey rows, in a very narrow window. Account deletion has the same pattern.

**Checked and found sound:**

- link tokens (primary only, single use, bound to the device ID, expiry);
- the account-row write in every transaction that changes an account's devices;
- the list's canonical decoding, signature coverage and version check (no wrap);
- entries forced to match enabled devices, so the primary can never be dropped;
- cross-account isolation;
- pending devices excluded from fetches and the send check;
- the identity key fixed at link time;
- link proofs and domain separation;
- the provisioning crypto (fresh ephemeral key per seal, low-order points refused, constant-time
  tag check);
- atomic single-use Lua scripts;
- parameterized SurrealQL;
- deletion coverage of the new tables;
- no identifiers in logs or metrics.

## Open risks

- Only the account's own devices are told when its list changes. The server keeps no social
  graph, so contacts learn through the send path's device check and list fetches.
- Until key transparency (M6), a first-time contact trusts the server for the account identity
  key that vouches for lists.
- A registry restore brings back devices removed after the backup. Clients refuse the restored
  list as a rollback, and the primary must sign again (runbook).
- Losing the primary means deleting the account until M4b's recovery and a primary transfer
  exist.
- Channel expiry rests on `valkey-hot`'s key expiry (`SET … EX`). The tests cover single use,
  unknown and already-read channels, not the ten-minute clock.
