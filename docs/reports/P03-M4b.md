## What was built

1. **Second factor on linking** (`crates/proto/src/devices.rs`, PROTOCOL.md §4.7). The link
   request carries an optional PIN or passkey assertion. Once an account has either factor,
   linking needs one. This is the step a QR-scan phisher cannot complete.
2. **Two-step PIN** (`services/api/src/devices.rs`, `crates/accounts/src/devices.rs`):
   - 6 to 12 digits, Argon2id under a pepper derived from the key directory's secret, compared in
     constant time;
   - each attempt counted in the account row's transaction before it is checked;
   - 5 free attempts, then doubling locks up to a week; unusable after 20 until the primary sets
     a new PIN.
3. **Passkeys** (`crates/keys/src/webauthn.rs`, Songbird's own verifier, the owner's choice):
   - a strict CBOR subset;
   - ES256 and EdDSA;
   - no attestation trusted;
   - user verification required by default;
   - counters compare-and-swapped;
   - single-use registration challenges;
   - link assertions whose challenge is derived from the link transcript.
4. **Only the primary** sets or removes factors. `GET /v1/account/factors` shows their state.
5. **Multiple accounts** on one installation are separate accounts with nothing shared. The
   shared APNs token is documented (PROTOCOL.md §4.7; threat model §6).
6. Docs: PROTOCOL.md §4.7; threat model §1 (two rows, awaiting approval), §3.13 and open risks;
   D-0053; settings in `[api.keys.devices]`; the fuzz target `devices` extended to WebAuthn.

## Tests

| Test | What it proves |
| --- | --- |
| `crates/keys` `webauthn_vectors` (2) | **The W3C WebAuthn Level 3 test vectors** (ES256 with no attestation, Ed25519 with packed attestation, copied from the specification's source) register and assert. Refused: another challenge, origin or RP ID; a flipped signature or authenticator-data byte; a counter that does not grow; registration data used as an assertion; user verification required of authenticators without it; a flipped RP ID hash or user-present flag. A flipped credential ID or key byte never yields the same credential |
| `crates/keys` `webauthn` unit tests | base64url against RFC 4648; CBOR refuses non-minimal integers, indefinite lengths, tags, simple values, duplicate keys and deep nesting |
| **`racing_pin_guesses_never_exceed_the_free_attempts`** (`crates/accounts`, live) | 40 parallel guesses over eight connections with 3 free attempts: exactly 4 reach the check. The count and lock are right; a correct PIN clears them; no PIN refuses |
| `services/api` `devices_live` (3 new) | PIN: shape, no factor, wrong PINs, the lock (even the right PIN refused until it ends), success resetting it, primary only, unusable after the limit until a new PIN. Passkey: registration with a single-use challenge, another origin refused, linking needs it, an assertion for another transcript refused, its own transcript approves, a cloned counter refused, removal lifts the requirement. Two accounts on one installation stay apart (devices, lists, factors, push indexes) |
| `crates/proto` | Link requests round-trip with each factor; truncations, trailing bytes and bad PINs refused |
| Fuzz `devices` (with WebAuthn) | 60 s, 3,075,994 runs, nothing found |

The full local runs (`cargo xtask ci fast` and the live suites) are in the final gate report,
`P03-gate.md`.

## Open risks

- The PIN stops a database or backup thief, not a fully compromised `api`. Hardware
  guess-limiting is issue #26 (Prompt 10).
- Passkeys sync through Apple or Google accounts; whoever controls that account can use the
  passkey.
- On iOS, several accounts on one phone share an APNs token, which links them at the push
  service.
- Recovery itself is Prompt 10's; the factors are ready for it.
