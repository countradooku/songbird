## Properties and their evidence

| Property | Evidence |
| --- | --- |
| A key copied loosely still reads; any one-character typo or adjacent swap is caught on the device | `recovery_keys_round_trip_forgive_formatting_and_catch_typos` (50 random keys) |
| Keys are independent; another key opens nothing | `different_keys_derive_unrelated_vaults`; `damaged_manifests_fail_loudly` (another key, another vault ID) |
| A backup restores exactly what was written, media included, each media file stored once | `a_backup_restores_exactly_what_was_written`; proptest `anything_written_reads_back` (48 cases, random chunk sizes, media streamed and small) |
| Incremental: an unchanged history uploads nothing; ten new messages per chat upload under a quarter of the first backup's chunks | `a_second_backup_uploads_only_what_changed` |
| Production parameters cut 1–8 MiB chunks | `production_parameters_cut_megabyte_chunks` |
| **Damaged chunks fail loudly**: a flipped bit anywhere, truncated, extended, emptied, missing, two swapped, or one from another backup | `damaged_chunks_fail_loudly` |
| **Damaged manifests fail loudly**: flipped bits, every truncation, a relabelled generation, a newer format, wrong lengths, a wrong stream hash | `damaged_manifests_fail_loudly` |
| A store cannot roll back or fork a device that has seen a backup | `a_store_cannot_roll_back_or_fork_a_device_that_has_seen_a_backup` |
| Nothing is written before every chunk is checked; staging changed after verification fails on read; staging on disk is encrypted | `staging_changed_after_verification_fails_on_read`; `a_folder_stages_large_backups_encrypted` |
| Byte-exact and platform-independent | `this_build_produces_the_published_bytes` (macOS arm64 here; Linux x86_64 and i686 in CI); `vectors/check.py` re-derives the key, every derived key, the chunk and the manifest from the specification with the Python standard library only |
| Newer readers read older backups | `this_reader_restores_every_published_version` |
| Decoders never panic on any input | fuzz `backup_format`: 1,001,749 runs in 120 s, no failure (nightly, libFuzzer, macOS arm64) |
| No service can link the format | `no_service_depends_on_the_backup_format` |
| `Debug` shows no content, key or name | `debug_output_never_shows_content`; every schema type prints its name only |

## Numbers

Apple M5 Pro, 48 GB, macOS 27.2.1 (Darwin 27.2.0), release build, one core
(`cargo test --release -p songbird-backup-format --test bench -- --ignored --nocapture`):

| Measure | Result |
| --- | --- |
| Keyed chunker | 3,735 MB/s; 109 chunks of 256 MB random data, 2.35 MiB on average |
| Seal a 2.35 MiB chunk (HMAC name, Padmé, XChaCha20-Poly1305) | 518 MB/s |
| Open and check it | 534 MB/s |
| Whole backup: 400,000 messages in 200 chats, 300 contacts, 8,003 distinct media files (9,302 MB plaintext), into memory | 4,621 chunks, 7,768 MB stored (compressible synthetic media stored once); written in 67.8 s (137 MB/s, the synthetic generator included); verified in 33.1 s; manifest 401,460 bytes |

The incremental cost on a large history, against the vault, is M4's measurement.

## Changes from the plan

- The manifest holds three stream kinds (records, small media, one stream per large media
  file) rather than one section per content type: one records stream in a canonical order lets
  the chunker resynchronise after any change, and puts small chats in shared chunks, so the
  object count does not reveal the number of chats.
- Media under 1 MiB are blobs in one shared stream; a file of 1 MiB or more is its own stream.
- The chunk plaintext carries its own length inside the padding; readers check the ciphertext
  length against the manifest before decrypting.
- `chacha20`, `poly1305`, and this crate are optimised in dev builds (`[profile.dev.package]`):
  unoptimised, the tests took 41 s instead of 2 s.

## Threat-model rows for the owner

Proposed for §3.27 (Backups, Prompt 10), marked awaiting the owner's approval:

| Threat | STRIDE | Attacker | Mitigation | Evidence |
| --- | --- | --- | --- | --- |
| A storage provider (Songbird included) reading a backup | I | Provider, insider, legal compulsion of the provider | Every chunk and manifest encrypted on the device with XChaCha20-Poly1305 under keys from the recovery key, which never leaves the user's devices; names are HMACs; sizes padded (Padmé) | `a_folder_stages_large_backups_encrypted`; vectors |
| Guessing the recovery key | S, I | Anyone holding the ciphertext | 256 random bits; HKDF; the 64-bit check only catches typos | `RecoveryKey::generate` (OS randomness) |
| Learning content from chunk boundaries or names | I | Provider | The chunker's gear table and the name key are derived from the recovery key | `another_key_cuts_elsewhere` |
| A damaged, truncated, swapped, foreign or missing chunk restored as data | T | Provider, storage fault, an attacker with write access | Name and version in the AAD; exact length check before decryption; HMAC of the plaintext must equal the name; stream lengths and SHA-256; two phases, nothing written until all checked | `damaged_chunks_fail_loudly`, `damaged_manifests_fail_loudly`, `staging_changed_after_verification_fails_on_read` |
| A provider serving an older backup | T | Malicious provider | The authenticated generation and the previous manifest's hash: a device that has seen a backup refuses older or forked ones; a brand-new device cannot tell (§6) | `a_store_cannot_roll_back_or_fork…` |
| A crafted manifest or stream crashing or exhausting the app | D | Malicious provider, a writer with the key | Bounds before allocation (manifest 48 MiB, 2^20 streams, 2^21 chunks, records 4 MiB, chunks 8 MiB); fuzzed decoders | fuzz `backup_format` |
| An older app half-reading a newer backup | T | — | `min_reader_version`: the whole backup is refused with "update Songbird" | `damaged_manifests_fail_loudly` (TooNew) |
