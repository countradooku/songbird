## Store decision: SurrealDB, Valkey, Apache Iggy

The owner asked for the best and fastest mailbox store after SurrealDB's ceiling. The same
`Mailbox` trait and closed-loop workload ran against each candidate: every write fsynced before
the store answers, ACK deletes included, client-style idempotent retries, 8 s per run, two
interleaved rounds, a `seq` check after every run (96 runs, all gap-free and duplicate-free).
Valkey 9.1.3 with AOF `appendfsync always`, one instance and four sharded by device; Iggy 0.10.0
with `durability = persisted`, four shards. On this disk and on tmpfs (no fsync cost: each store's
own ceiling). Sends/s, best of two rounds (D-0029 has the full table):

| Workload | SurrealDB | Valkey ×1 | Valkey ×4 | Iggy | Iggy, tmpfs | Valkey ×4, tmpfs |
| --- | --- | --- | --- | --- | --- | --- |
| 1 sender | 273 | 1,403 | 1,346 | 368 | 8,868 | 26,313 |
| 128 senders | 6,272 | 36,261 | 42,346 | 15,612 | 444,717 | 259,046 |
| 1,024 senders | 7,088 | 42,378 | 123,670 | 153,128 | 1,410,584 | 337,594 |
| 10-device sends, entries/s | 7,271 | 93,156 | 81,500 | 163,044 | 1,909,177 | 348,316 |
| 100-device groups, entries/s | 3,458 | 160,031 | 242,598 | 647,467 | 4,766,768 | 548,448 |

Iggy has the highest ceiling by far; Valkey the lowest latency for a lone send. The owner chose
Iggy and asked for it built for production (D-0029) with the official SDK (D-0030).

### Degraded modes on Iggy

- **Reconnect chaos**: 10,000/s offered for 20 s, a random connection dropped every 20 ms and all
  1,000 at once at 10 s: 84,057 accepted, 5,370 retried sends, 1,949 aborts, **0 lost, 0
  duplicates, 0 order violations**.
- **Iggy frozen for 8 s** (SIGSTOP) in a 20 s run at 2,000/s: sends stall and resume; 23,214
  accepted, 0 rejected, **0 lost, 0 duplicates, 0 order violations**; max latency 9.3 s.
- **`delivery` restart**: ready again after 0.42 s (replay), then 5,000/s offered: **0 lost**.
- **Unreadable log**: `delivery` refuses to start and names the partition, offset and record
  version (checked against a log written before the format change).
- **Disk full** (seen on tmpfs during the comparison): Iggy's affected shards refuse to commit and
  the server stops; Valkey exits on an AOF write error. Neither loses acknowledged data.

Each sender waits for its send's answer before the next one; a commit is one fsynced transaction.

| Senders | Sends/s | Commits/s | Sends per commit | p50 | p99 | p99.9 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 303 | 303 | 1 | 3.3 ms | 4.1 ms | 4.8 ms |

| 128 | 11,557 | 90 | 128 | 10.8 ms | 15.1 ms | 17.9 ms |

How we got here (same benchmark, `max_wait` 1 ms):

| Design | 1 sender | 128 senders | 1,024 senders |
| --- | --- | --- | --- |
| First: one transaction with `FOR` loops and closures computing `seq`s in SurrealQL | 129/s, 7.7 ms | 3,900/s | 3,393/s |
| Cached counters, bulk statements, compare-and-set guard (durable) | 228/s, 4.4 ms | 10,473/s | 14,130/s |
| Same, in-memory engine | 253/s, 3.9 ms | 11,831/s | 16,806/s |
| Final, `max_wait` 0 (durable) | 303/s, 3.3 ms | 11,557/s | 12,572/s |

The in-memory engine is only about 10–20 % faster than the durable one: SurrealDB's execution, not
fsync, sets the ceiling.

## Bugs found and fixed during the milestone

Iggy mailbox (found by the end-to-end runs and the store comparison):

- **`seq` reuse after a format change.** Replay skipped records it could not decode, with a
  warning; after the record format changed without a version bump, 684,229 records were skipped,
  counters restarted, and clients dropped every new message as already seen (the checker reported
  them all lost). Replay now refuses to start on any unreadable record; the format version is 2
  and bumped on every change (`start_up_refuses_an_unreadable_log`).
- **Every send was two appends.** The home partition was derived from the idempotency key, so a
  1:1 send usually wrote a home record on one partition and its entry on another; after a restart
  the re-driver re-sent thousands of parts and `delivery` idled at 64 % CPU with 11 s connects.
  The home is now the partition holding most recipients, and only missing parts are re-driven.
- **Compaction blocked sends.** It read old records one poll at a time inside the partition's
  writer. It now runs in a compactor task on its own connection, many records per poll, at most
  100,000 entries per pass; sends never wait on it.
- **A reused key could replay the wrong send.** A part record held only its partition's devices,
  so a reuse for exactly those devices looked like a retry. Records now carry a fingerprint of
  the whole recipient set.
- **Retries were not reported as replays**, and the SDK's own logs put the server address in the
  log stream (inv6 caught it): both fixed.
- **Benchmark artefact, recorded so it is not mistaken for data loss:** the Valkey client's 500 ms
  default response timeout gave up on writes Valkey had committed; the `seq` check then saw gaps.
  The benchmark now retries like a client (same key, original `seq`s back).

SurrealDB mailbox (first design):

- Store and ACK transactions both wrote the per-device counter record and aborted each other on
  SurrealDB's optimistic conflict check (55 s for a 1-second test). Separate `ackctr` records, then
  a single writer: 1.0 s.
- Under saturation the writer's send-biased loop starved ACK flushes; the queue then dropped ACKs,
  entries were never deleted and a later run hit the capacity limit (10,000 sends rejected).
  Queued ACKs are now taken on every wake-up; re-run passes.
- Shared-body reference counts were decremented in a separate transaction from the entry delete.
  Now one transaction.
- `SCHEMAFULL` tables refuse unknown fields: the compare-and-set `prev` field is defined.
- Parallel test start raced the schema definition: connect retries it for about 10 s.

## Open risks and follow-ups

1. **Acknowledged ciphertext stays on disk up to about 14 hours** (6-hour idempotency window plus
   8-hour segment expiry, both configurable) instead of being deleted on ACK (D-0029).
2. **Iggy is pre-1.0**: its storage format changed between 0.9 and 0.10; upgrades need care
   (runbook). Its container needs io_uring allowed in seccomp (the profile adds only those three
   syscalls).
3. **Supply chain**: the official SDK added 153 exempted crates and `ring` (unused by our TLS and
   crypto); audit `iggy`, `iggy_common`, `iggy_binary_protocol` first (D-0030).
4. **Tails and overload on this disk**: sub-second p99.9 and erratic throughput past saturation,
   caused by btrfs fsync stalls; to be measured on the reference hardware, with admission control
   in M3/M7.
5. **One delivery node per Iggy topic** until M4 (a second one is fenced and goes unready).
6. **Root credentials** to Iggy; least privilege is Prompt 12's. Iggy has server TLS and a
   password, no client certificates.
7. **Static device directory** still; the identity service (Prompt 3) owns devices, accounts and
   key versions. `delivery` stays not deployable.
8. **MLS commit authorization** (who may commit to a group) is Prompt 5's.
9. The production Iggy path reaches 60–90 % of the spike's tmpfs ceiling (idempotency lookups,
   home records, cache); sends spanning partitions cost two fsyncs in sequence. M3 profiles and
   trims both.
10. Not yet built: runtime, per-core resources, zero allocation (M3); Valkey routing (M4); push
    for offline devices (M5); restore and resend (M6).
