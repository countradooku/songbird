# Backups, restore and the store generation

Design: D-0040. Targets: registry RPO ≤ 5 minutes, RTO ≤ 2 hours. Tools: `songbird-admin backup`,
`songbird-admin generation`, `deploy/bin/backups-up`, `deploy/ansible/backup-verify.yml`.
Drill: `bench/m6/restore-drill.sh` (results in [drills.md](drills.md)).

What exists, in one paragraph: every 5 minutes the data host exports the SurrealDB registry as a
read-only `VIEWER` user, encrypts the export with age to two recipients (the owner's offline
identity, the verification identity) and puts it in the environment's off-site bucket at Scaleway
with Object Lock in compliance mode (frequent exports 25 h, the first of each day 8 days, of each
week 29 days, of each month 93 days). The data host can only put: it cannot read, list or delete a
backup and holds no key that decrypts one. A host in an environment of its own restores the newest
backup daily into a throwaway database and checks it. **The mailbox is never backed up**: after a
restore, or any loss of the mailbox, the store generation is increased and clients resend every
message that has no delivery receipt (PROTOCOL.md §3.6).

Everything that changes the registry (`backup restore`, `generation bump`, `accounts import`)
needs `--confirm <namespace>/<database>` and writes `/var/log/songbird/admin-audit.jsonl`. Copy the
lines of an incident into its report.

## Setup (once per environment, owner)

1. Create the age identities, offline, on a machine that is not a server:
   - the **owner identity**: `age-keygen -o owner.key` on a hardware-backed key or an air-gapped
     machine; print the file on paper; store paper and device in two places. This is the only key
     that can decrypt backups after a disaster. Never copy it to a server.
   - the **verification identity**: `age-keygen -o verify.key`; it goes only into
     `deploy/secrets/<env>.backup-verify.sops.yaml` (owner-only recipients, `deploy/bin/sops-config`).
2. `deploy/secrets/backups.sops.yaml` (owner-only): `tofu_state_passphrase`,
   `state_access_key_hetzner`, `state_secret_key_hetzner`, `scw_access_key`, `scw_secret_key`,
   `scw_organization_id` (an Organization-level key) and `admin_principal` (`user_id:<uuid>`).
3. Choose the bucket name in `deploy/tofu/environments/<env>.backups.tfvars`, then
   `deploy/bin/backups-up <env>`. It creates the project, bucket, lock, lifecycle, both
   applications and their keys.
4. Into `deploy/secrets/<env>.sops.yaml`: `backup_s3_bucket`, the **writer** key as
   `backup_s3_access_key` / `backup_s3_secret_key`, and `backup_age_recipients: [<owner age1…>,
   <verify age1…>]`. `backup_surreal_password` was generated by `secrets-init`.
5. Into `deploy/secrets/<env>.backup-verify.sops.yaml`: `backup_s3_bucket`,
   `backup_verify_identity` (the `AGE-SECRET-KEY-…` line), and the **verifier** key as
   `backup_verify_s3_access_key` / `backup_verify_s3_secret_key`.
6. Deploy the environment (`env-up` or `rollout`): the `backup` role creates the read-only user,
   installs the timer and runs one backup; the play fails if that backup fails.
7. Build the verification environment (`deploy/bin/env-up <env>-verify <cloud>`; it has one host
   with the `bastion` and `verify` roles), then as the owner:
   `ansible-playbook -i inventory/generated/<env>-verify.yml backup-verify.yml -e verified_env=<env>`.
   It runs one verification at the end.
8. Check that the provider enforces what tofu configured, once, with the writer key: a `GET`, a
   `LIST`, a `DELETE` and a `PUT` with `x-amz-acl: public-read` are all refused; a `DELETE` with the
   owner's key on a locked version is refused until its retention date.

## Backups failing (timer)

- Detection: `systemctl status songbird-backup.service` failed on the data host; the daily
  verification fails because the newest backup is older than 1 hour.
- Impact: none for users while the registry is healthy; the RPO grows until fixed.
- Actions:
  1. `journalctl -u songbird-backup.service -n 50` on the data host.
  2. SurrealDB refused: check the `backup` user (re-run the `backup` role; it redefines the user
     with `OVERWRITE`).
  3. S3 refused: key revoked or bucket policy changed: compare with `deploy/tofu/envs/backups`
     (`backups-up` re-applies it).
  4. `systemctl start songbird-backup.service` and wait for success.
- Verification: a new object under `registry/frequent/`, then the next verification passes.

## Verification failing (daily)

- Detection: `songbird-backup-verify.service` failed on the verification host.
- Actions by message:
  - `newest backup is N hours old`: the timer is not running; see above.
  - `the bucket shows tampering`: a name was written twice, or a backup's name claims another
    time than the server stored it at. The writer key can put but never overwrite legitimately:
    treat it as a compromise of the data host (below). Restores are safe meanwhile: they read the
    **first** stored version of each name and ignore misdated ones; the warning and the counts
    are in the audit log.
  - `decryption failed`: the verification identity is not among the recipients
    (`backup_age_recipients`): fix and redeploy; old backups age out.
  - `N statements of the import failed` or `inconsistent` (devices without an account, generation
    0): the backup itself is bad. Keep the object name; check older backups with `--object`. A
    registry that exports inconsistent data is an incident of its own: inspect it before the
    next export ages out the good ones.
- Verification: `systemctl start songbird-backup-verify.service` succeeds.

## SurrealDB data loss or corruption (restore)

- Detection: the registry is unreachable with its volume damaged, statements fail with storage
  errors, or data is wrong (operator error).
- Impact: while it is down, delivery keeps sessions and refuses sends retryably; new devices
  cannot authenticate. No message is lost: the mailbox is separate, and clients resend after the
  restore anything that was lost with it.
- Immediate actions:
  1. **Stop writes:** stop `api` and `worker` (`docker stop songbird-api songbird-worker`) and
     delivery on every node. A restore goes into an **empty** database; `songbird-admin`
     refuses one with tables.
  2. Note the time. Save the audit log and `journalctl -u songbird-surrealdb` for the report.
- Recovery (about 10 minutes plus 1 minute per million accounts; measured in drills.md):
  1. Fetch the backup to the operator machine with the verifier key, or with the owner's key if
     the verification host is unavailable (`aws s3 cp` against `s3.fr-par.scw.cloud`, or
     `songbird-admin backup restore … --s3-addr … --s3-tls` with `BACKUP_S3_*` set to a reading
     key). For operator error, restore from **before** the mistake: `--before
     <YYYYMMDDTHHMMSSZ>` (by the time the server stored each backup, which the uploader cannot
     choose) or `--object registry/<tier>/<time>-<id>.surql.age`.
  2. Remove the damaged database (`REMOVE DATABASE songbird;` as root) or start SurrealDB on a new
     volume.
  3. On a host that reaches SurrealDB, with the owner identity on a hardware key or a temporary
     file on an encrypted, non-server machine:

     ```bash
     SURREAL_PASS=… songbird-admin backup restore --addr <data>:8000 --host surrealdb.<fqdn> \
       --tls-ca ca.crt --namespace songbird --database songbird \
       --s3-addr s3.fr-par.scw.cloud:443 --s3-tls --s3-bucket <bucket> \
       --identity owner.key --age age --max-age-hours 2160 \
       --confirm songbird/songbird --audit-log ./admin-audit.jsonl
     ```

     It decrypts in memory (the plaintext never reaches disk), imports, checks the result and
     **bumps the store generation**.
  4. Redeploy the services (`deploy/bin/rollout <env> <current version>`) so the `backup` role
     re-checks its user and the services start.
  5. **Deletions after the backup:** an account deleted between the backup and the loss is back
     in the registry. A deletion job still queued in `valkey-jobs` runs again and removes it; a
     finished one left no record (done jobs are deleted, by design), so that account stays
     restored, with an empty mailbox and no push token. This is at most 5 minutes of deletions
     for the newest backup, more for an older one. Record it in the incident report (open risk
     in P02-M6: a deletion journal is an owner decision).
- Verification:
  - `songbird-admin generation show` is larger than before;
  - delivery's `/readyz` on every node; clients reconnect and resend (`StoreGenerationChanged`);
  - the next backup and a manual verification (`systemctl start songbird-backup-verify.service`)
    pass.
- Follow-up: report with the audit-log lines and the measured outage.

## Mailbox lost (Iggy data or a node's key store)

- Detection: Iggy's volume lost; a node's `key_dir` or master key lost without a standby copy
  (D-0031, D-0034).
- Impact: pending messages on the lost partitions cannot be delivered from the server.
- Actions:
  1. Bring Iggy (or the node) back empty.
  2. `songbird-admin generation bump --confirm songbird/songbird` against the registry. Every
     client resends what has no delivery receipt; recipients drop repeats by message ID; a
     surviving partition replays its idempotency records, so nothing is stored twice.
- Verification: clients report `StoreGenerationChanged`; the mailbox refills; the delivery checker
  in staging (`bench/m6/restore-drill.sh`) shows no loss for the same failure.

## Whole server or provider lost

1. Rebuild at the other provider: [provider-switch.md](provider-switch.md).
2. Restore the registry as above, from the off-site bucket (it is at a third location from the
   environment and from the state).
3. Bump the generation (the restore does it); the mailbox starts empty and clients resend.
4. Time it against the 2-hour RTO and record it in [drills.md](drills.md).

## Compromise or ransomware

- The data host cannot read, list or delete backups; compliance-mode retention cannot be shortened,
  even by the owner. A compromised production server cannot destroy them.
- Rebuild clean from `deploy/`, rotate every secret ([secrets-rotation.md](secrets-rotation.md)),
  restore with `--before <time of the compromise>`, bump the generation. Backups stored after
  the compromise began are untrusted: the attacker held the writer key and the public recipients,
  so they could upload well-formed backups of their own. Overwrites of older names cannot hide
  the originals (restores read the first version; verification reports them).
- If the verification host or its SOPS file is compromised: the attacker can read every backup
  still retained (registry metadata of up to 93 days, including deleted accounts). Revoke the
  verifier key (`backups-up` after deleting the key in the console), create a new verification
  identity, replace it in `backup_age_recipients`, redeploy. Old backups stay readable to the old
  identity until they expire; record the exposure.

## Rotating the identities

- Verification identity: new key pair, replace the public key in `backup_age_recipients` and the
  secret in `<env>.backup-verify.sops.yaml`, redeploy both. Backups encrypted to the old one expire
  within 93 days; keep the old secret until then for restores.
- Owner identity: the same, but keep the old identity offline until the last backup encrypted to
  it has expired (93 days).
