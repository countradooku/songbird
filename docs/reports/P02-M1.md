## Numbers

Reproduce with `tools/loadgen/bench/m1.sh <sockudo-ws-3.1.1 source>`; full output of the run
below is quoted from that script. Every load-generator run passed the checker.

### WebSocket layer versus sockudo-ws (echo round trips, 256-byte binary messages, 10 s)

Server: one thread pinned to CPU 0. sockudo-ws is its own `simple_echo` example built from the
3.1.1 source with `TOKIO_WORKER_THREADS=1`; Songbird is `songbird-delivery-autobahn` (our upgrade,
limits, buffers and current-thread runtime). Same client (`songbird-loadgen echo`, 8 threads).

| Load | Server | msg/s | p50 | p99 | p99.9 |
| --- | --- | --- | --- | --- | --- |
| 100 connections, 1 in flight | sockudo-ws | 156,441 | 649 µs | 691 µs | 893 µs |
| 100 connections, 1 in flight | Songbird | 158,374 | 630 µs | 704 µs | 919 µs |
| 1,000 connections, 4 in flight | sockudo-ws | 177,401 | 4.9 ms | 65.1 ms | 75.6 ms |
| 1,000 connections, 4 in flight | Songbird | 171,744 | 14.7 ms | 20.6 ms | 20.8 ms |

Our layer adds no measurable cost at moderate load (within run-to-run noise of about 2 %) and is
3 % lower in saturated throughput, with a much tighter tail (p99 20.6 ms against 65.1 ms) because
every wake-up writes and flushes once per connection.

### Delivery end to end, one thread

Real client per device; 1,000 devices; each sends 1:1 to random peers at an equal share of the
offered rate, waits for `SendResult`, and acknowledges every delivery. Path: `Send` frame →
in-memory store (M1 stand-in) → `SendResult` → route → `Deliver` → coalesced `Ack` → delete.
Latency is send to deliver as the client observes it (includes both client stacks).

| Offered | Achieved | p50 | p99 | p99.9 | max | Server process CPU per 10,000 messages |
| --- | --- | --- | --- | --- | --- | --- |
| 10,000/s | 9,998/s | 216 µs | 576 µs | 1.09 ms | 1.75 ms | 154 ms |
| 30,000/s | 29,980/s | 642 µs | 1.41 ms | 2.94 ms | 7.79 ms | 128 ms |
| 60,000/s | 59,887/s | 5.1 ms | 17.2 ms | 26.2 ms | 36.6 ms | 110 ms |
| 100,000/s | 68,755/s (saturated) | 21.8 ms | 29.2 ms | 30.0 ms | 33.0 ms | 95 ms |

At saturation CPU 0 is 100 % busy: 17 % user, 48 % system calls, 35 % softirq (loopback packet
processing, not charged to the process; measured from `/proc/stat` over 5 s). The load generator
used 0.7 cores in total, so it is not the limit. One core carries about 69k end-to-end messages
per second (each one inbound `Send`, two outbound frames and a share of an `Ack`), and the cost is
mostly the kernel: milestone 3's levers are more cores and fewer syscalls per message.

### Reconnect chaos and storm

1,000 devices, 10,000 msg/s for 20 s; one random connection dropped every 20 ms, and every
connection dropped at once at 10 s: 1,949 drops, 199,987 messages accepted, 2,130 retried sends
(same idempotency key), **0 lost, 0 duplicates, 0 order violations**; p50 226 µs, p99 4.8 ms,
p99.9 71 ms, max 129 ms (the storm). All 1,000 devices reconnected (no client failed).

### Memory per idle connection

Fresh server, 10,000 authenticated devices connected and idle: RSS 49.9 MB → 243.8 MB, **about
19.9 KB per connection** (4 KiB read buffer, 4 KiB write buffer, WebSocket state, session, two
inbox channels, task; mimalloc). M3 measures and shrinks it (lazy buffers released when idle).

### Not measured yet

p99.9 per hop (same core, cross-core, cross-node) and SurrealDB commits per second need M2–M4.
No flamegraph (no `perf` on the machine; see risks).

## Bugs found and fixed during the milestone

- The client did not flush its coalesced ACK on a clean close, so the last few milliseconds of
  deliveries stayed in the mailbox and were redelivered on the next connection. Found by the
  checker (a reconnect run on a server reused from an earlier run reported 176 "unexpected"
  deliveries). Fixed; the load generator now tags payloads with a run ID so leftovers from an
  earlier run are reported separately.
- After a restore from backup the client kept its old resume point and would have dropped new
  envelopes whose `seq` the restored server reused. Fixed (reset on a larger store generation);
  test `store_generation_change_resets_resume_point`.
- A retried send answered from the idempotency record was not routed again, so a route lost
  between store and route waited for the 120 s safety sweep. Now routed again (duplicates dropped
  by the recipient's cursor).
- An oversized upgrade request got `400` instead of `431`.

## Open risks and follow-ups

1. **The single-thread ceiling is the kernel.** At ~69k end-to-end messages/s CPU 0 is 100 % busy,
   over 80 % of it in syscalls and loopback softirq. Milestone 3 (thread-per-core, `SO_REUSEPORT`)
   and fewer flushes per message are the levers; measure syscalls per message there.
2. **Stand-ins.** The in-memory mailbox and the in-process router each take a `Mutex` per
   operation, which the constitution forbids on the hot path; they go away in M2 and M3 (D-0021).
   Nothing here is durable, and the static device directory is refused outside development and
   CI, so `delivery` is not deployable until M2 and Prompt 3. The Ansible service template has no
   `[delivery]` section yet.
3. **One envelope copy per delivery** (header plus envelope in one WebSocket message). M3 removes
   it with a vectored header segment.
4. **Per-session Tokio timers** (safety sweep, write timeouts). M3 measures a per-core sweep.
5. **Supply chain.** 22 new cargo-vet exemptions; sockudo-ws (parses every client byte, `unsafe`
   SIMD) and quanta are the ones to audit first (D-0017).
6. **No flamegraph.** `perf` is not installed on the measurement machine (`sudo dnf install perf`,
   then `cargo flamegraph`); the CPU-0 breakdown above stands in for it.
7. **Sockudo server baseline** not done (owner decision below).
8. Not yet built (later milestones): SurrealDB mailbox and group commit, batched ACK deletes,
   device lists and MLS ordering (M2); runtime, per-core resources, zero allocation (M3); Valkey
   routing (M4); push jobs for offline devices (M5); restore and resend (M6).
