## What was built

1. **`POST /v1/registration/challenge` and `POST /v1/registration`** (`services/api/src/registration.rs`,
   PROTOCOL.md §4.1). An account is created with a server-chosen ID, an **account identity key**
   and its first device (server-chosen ID, **authentication key**), each key proving possession by
   signing a transcript that names the server, the single-use challenge and both keys under its own
   context. Checks run cheapest first; every refusal says only what the client needs to recover.
2. **Argon2id proof of work** (`crates/pow`, new): stateless, MAC'd 51-byte challenges valid
   10 minutes and once; `k` strictly increasing solutions of `b` leading zero bits each;
   verification off the async runtime, bounded, stopping at the first failure. Defaults measured
   below.
3. **Honest keys only** (`crates/keys`, new): every Ed25519 key the server stores must be the
   canonical encoding of a prime-order point. Found while building: aws-lc-rs alone accepts a
   signature under the identity point for any message, so a device registered with that key could
   be impersonated by anyone. Registration and the admin link refuse such keys.
4. **Per-IP-range throttles**: GCRA in `valkey-hot` under a keyed hash of the range (IPv4 `/24`,
   IPv6 `/48`), per range and deployment-wide, for challenges, registrations and refused invite
   codes; fail closed. The listener passes the client address to registration and nowhere else.
5. **Invite-only launch** (D-0038, D-0047, PROTOCOL.md §4.2): a setting, no migration; 120-bit
   codes stored as SHA-256 hashes with uses and expiry only (no creator, no user); single- and
   multi-use; atomic redemption; user codes from a per-account allowance (`POST`, `GET`,
   `DELETE /v1/invites`); operator batches (`songbird-admin invites create`, `invites grant`,
   audit-logged without the codes); the worker sweeps expired codes.
6. **Registry** (`crates/accounts`): `account.identity`, `account.invites`, table `invite`;
   `register` (one transaction with the invite), user and operator invites, revocation, sweep.
   SurrealDB 4 reports a lost write conflict as a generic `Query` error that "can be retried":
   now classified and retried (found by the race test).
7. **Client** (`songbird_api::client::Registrar`, `songbird_client::ClientConfig::new_device_grace`):
   the whole registration flow, and a grace period during which a fresh device retries close 4000
   while delivery's directory catches up (found by the end-to-end test; the alternative, delivery
   querying the registry for unauthenticated connections, was refused as a denial-of-service lever).
8. **Docs:** PROTOCOL.md §4.1, §4.2 and §13 vectors; threat model §1 (four rows, awaiting the
   owner), §3.8 (registration-time account takeover, enumeration and key substitution, each with
   mitigation and test), §6; runbook "Registration refusing or throttling sign-ups"; DECISIONS
   D-0047, D-0048; `config/dev/api.toml`.

## Numbers

Argon2id, release build, one core of the Apple M5 Pro (`cargo run --release -p songbird-pow
--example timing`), median of 41 evaluations:

| Memory | Passes | Per evaluation |
| --- | --- | --- |
| 4 MiB | 1 | 1.39 ms |
| 8 MiB | 1 | 2.25 ms |
| **16 MiB** | **1** | **4.23 ms** |
| 32 MiB | 1 | 9.08 ms |
| 8 MiB | 2 | 3.91 ms |
| 16 MiB | 2 | 8.17 ms |

**Defaults: 16 MiB, one pass, 8 solutions of 4 bits** (128 evaluations on average). Solving 30
challenges: p10 0.29 s, median 0.48 s, p90 0.76 s, max 0.82 s. Verifying all 8 solutions: 31.4 ms,
so one core verifies about 30 registrations a second. Memory-hardness: each evaluation touches
16 MiB, which limits how many a GPU runs at once. A phone core is several times slower than this
Mac's, which puts the defaults at a few seconds there; that is an estimate until the apps exist.
Challenges carry their parameters, so retuning is a configuration change.

No hot-path code changed (delivery's send and delivery paths are untouched; the client change is
in its reconnect decision).

## Security review

`security-review` over the uncommitted diff (an independent reviewer, read-only): **no finding
at or above the reporting bar**. It checked SurrealQL injection (every new query binds its
variables; the one `format!` inserts a constant fragment), challenge forgery and replay (MAC over
every parameter, constant-time comparison, the nonce burnt for longer than any challenge can be
accepted), signature and key checks, invite atomicity and enumeration, `/v1/invites`
authorization (the account comes from the authenticated device, never the request), and data
exposure (codes never in `Debug` or logs; throttle records hold no address). Two notes below its
bar, both by design: an account being deleted can still create invites until its devices are
disabled (the same transaction that starts the deletion), and a holder of a multi-use operator
code can revoke it for everyone (whoever holds a code may revoke it).

## Open risks

- Phone timing of the proof of work is estimated, not measured (no app yet).
- Per-range throttles count everyone behind one carrier NAT or a TCP-relaying censorship proxy as
  one client; the numbers are generous and the deployment-wide caps stand behind them.
- A registry restore revives invite codes used after the backup until they expire.
- Eight new crates are exempted in `cargo vet` pending audits (D-0048 lists the backlog).
- The account identity key signs nothing yet: the signed device list is M4. Until then the server
  stores it and proves only that the registrant held it.
