## Numbers

From `gate_p06::media_load`, release build, p50 / p99. The machine and stack are in D-0081.

| Measurement | Result |
| --- | --- |
| 1 MiB upload, one at a time | grant 4.6 ms; PUT through `api` 58 ms; PUT straight to RustFS 53 ms |
| 1 MiB, concurrency 1 | upload 64 / 75 ms; download 5.0 / 9.1 ms; 36 MB/s each way |
| 1 MiB, concurrency 16 | upload 44 / 125 ms; download 9.2 / 13.9 ms; 486 MB/s each way |
| 1 MiB, concurrency 64 | upload 136 / 187 ms; download 44 / 56 ms; 684 MB/s each way |
| 1 MiB GET, 32 in flight | RustFS directly 9.1 / 12.1 ms; through `api` 21.8 / 31.3 ms |
| 64 MiB | upload (parallel parts) 277 MB/s; download 775 MB/s |
| 128 KiB ranges, 8 in flight | 4.0 / 5.6 ms |

**Reading the numbers:**

- Upload latency is RustFS's own write in this VM. `api` adds the grant (about 5 ms).
- Downloads and seeks are fast enough for streaming video and voice notes.
- No caching proxy is justified (D-0082): RustFS is a minority of a download's time, and an
  attachment is read by its few recipients only.
- These numbers include podman's WSL 2 port forwarding. Prompt 13 measures again on the
  production hardware.

## Open risks

- A media URL can be read as often as one likes for its 10 minutes. Range requests are cheap,
  but a client could use a URL to burn egress. Prompt 11's abuse limits can budget media bytes
  per IP range if that shows up.
- The IP address of a downloader reaches `api`, as any HTTPS request's does. It is neither
  logged nor stored. The censorship-resistant proxy (D-0011) and Prompt 12 cover hiding it
  further.
