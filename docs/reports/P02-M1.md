## Decisions settled at the gate review (D-0024)

Researched against primary sources (Signal-Server `main`, the WhatsApp Encryption Overview of
2026-10-30, RFC 9266):

| Question | Signal | WhatsApp | Songbird now |
| --- | --- | --- | --- |
| Slow consumers | Store is the truth; notifications only wake the reader; at most 256 un-acked messages in flight; never actively disconnects a slow client | Not documented | Same model (lag flag, re-read the mailbox), plus Signal's 256 un-acked window; close 4100 only after 30 s without write progress |
| Retried sends | No server-side dedupe; clients drop duplicates (libsignal, sender + timestamp) | Not documented | Server record kept 6 h under HMAC(server secret, key), scoped to the recipient devices (reuse elsewhere refused, reason 7); apps still dedupe by message ID |
| Device authentication | HTTP Basic with a per-device random token stored as a salted hash (a bearer secret) | Noise Pipes, per-device static Curve25519 key; server holds the public key only; bound to the session by Noise | Per-device Ed25519 key, public key only on the server, challenge signature that now covers the TLS exporter (RFC 9266), the property Noise gives WhatsApp |

## Numbers

Reproduce with `tools/loadgen/bench/m1.sh <sockudo-ws-3.1.1 source>`. Every load-generator run
passed the checker. Figures below are from the final code (after the flamegraph fixes).

### WebSocket layer versus sockudo-ws (echo round trips, 256-byte binary messages, 10 s)

Server: one thread pinned to CPU 0. sockudo-ws is its own `simple_echo` example built from the
3.1.1 source with `TOKIO_WORKER_THREADS=1`; Songbird is `songbird-delivery-autobahn` (our upgrade,
limits, buffers and current-thread runtime). Same client (`songbird-loadgen echo`, 8 threads).

| Load | Server | msg/s | p50 | p99 | p99.9 |
| --- | --- | --- | --- | --- | --- |
| 100 connections, 1 in flight | sockudo-ws | 158,133 | 643 µs | 690 µs | 714 µs |
| 100 connections, 1 in flight | Songbird | 159,583 | 626 µs | 672 µs | 710 µs |
| 1,000 connections, 4 in flight | sockudo-ws | 177,647 | 4.9 ms | 64.6 ms | 75.2 ms |
| 1,000 connections, 4 in flight | Songbird | 177,154 | 14.5 ms | 20.4 ms | 20.5 ms |

Our layer costs nothing measurable (throughput within 1 %, three runs agree within about 3 %),
with a much tighter tail under saturation (p99 20.4 ms against 64.6 ms) because every wake-up
writes and flushes once per connection.

### Delivery end to end, one thread

Real client per device; 1,000 devices; each sends 1:1 to random peers at an equal share of the
offered rate, waits for `SendResult`, and acknowledges every delivery. Path: `Send` frame →
in-memory store (M1 stand-in) → `SendResult` → route → `Deliver` → coalesced `Ack` → delete.
Latency is send to deliver as the client observes it (includes both client stacks).

| Offered | Achieved | p50 | p99 | p99.9 | max | Server process CPU per 10,000 messages |
| --- | --- | --- | --- | --- | --- | --- |
| 10,000/s | 9,996/s | 200 µs | 526 µs | 833 µs | 1.82 ms | 148 ms |
| 30,000/s | 29,978/s | 579 µs | 1.18 ms | 2.65 ms | 7.80 ms | 120 ms |
| 60,000/s | 59,908/s | 2.9 ms | 17.9 ms | 28.3 ms | 37.9 ms | 108 ms |
| 100,000/s | 73,449/s (saturated) | 20.4 ms | 27.9 ms | 28.9 ms | 31.1 ms | 89 ms |

At saturation CPU 0 is 100 % busy: 17 % user, 48 % system calls, 35 % softirq (loopback packet
processing, not charged to the process; measured from `/proc/stat`). The load generator used 0.7
cores in total, so it is not the limit. One core carries about 73k end-to-end messages per second
(each one inbound `Send`, two outbound frames and a share of an `Ack`); most of the cost is the
kernel, so milestone 3's levers are more cores and fewer syscalls per message.

### Flamegraph

[`flamegraphs/P02-M1-delivery-1core-saturated.svg`](flamegraphs/P02-M1-delivery-1core-saturated.svg):
saturated run, user-space cycles, frame-pointer build. Share of user-space CPU by component:

| Component | Before fixes | After |
| --- | --- | --- |
| `Bytes` reference-count atomics | 15 % | 18 % |
| Router inbox (Tokio mpsc) | 13 % | 13 % |
| Socket reads (sockudo-ws) | 10 % | 11 % |
| In-memory store (stand-in) | 8 % | 10 % |
| Stand-in `Mutex` lock/unlock | 10 % | 8 % |
| Tokio timers | 9 % | 6 % |
| Hash maps (per send) | 8 % | 5 % |
| Idempotency HMAC | — | 2 % |

Fixed now: the safety-sweep timer was re-created on every wake-up (now one timer per session,
re-armed in place) and duplicate-recipient checks allocated a `HashSet` per send (now pairwise for
up to 32 recipients). Effect: saturation 68.8k → 73.4k msg/s (+7 %), p99 at 10k msg/s 576 → 526 µs.
Left for M2/M3: the stand-ins' mutexes and maps (replaced), `Bytes` and channel atomics
(shared-nothing per core), per-write timeouts.

### Reconnect chaos and storm

1,000 devices, 10,000 msg/s for 20 s; one random connection dropped every 20 ms, and every
connection dropped at once at 10 s: 1,949 drops, 199,919 messages accepted, 3,002 retried sends
(same idempotency key), **0 lost, 0 duplicates, 0 order violations**; p50 213 µs, p99 10.2 ms,
p99.9 92 ms, max 184 ms (the storm). All 1,000 devices reconnected (no client failed).

### Memory per idle connection

Fresh server, 10,000 authenticated devices connected and idle: RSS 50.2 MB → 257.2 MB, **about
21 KB per connection** (4 KiB read buffer, 4 KiB write buffer, WebSocket state, session, two
inbox channels, task; mimalloc). M3 measures and shrinks it (buffers released when idle).

commits per second need M2–M4.

## Bugs found and fixed during the milestone

- The client did not flush its coalesced ACK on a clean close, so the last few milliseconds of
  deliveries stayed in the mailbox and were redelivered on the next connection. Found by the
  checker (176 "unexpected" deliveries on a reused server). Fixed; payloads now carry a run ID so
  leftovers from an earlier run are reported separately.
- After a restore from backup the client kept its old resume point and would have dropped new
  envelopes whose `seq` the restored server reused. Fixed; `store_generation_change_resets_resume_point`.
- A retried send answered from the idempotency record was not routed again, so a route lost
  between store and route waited for the 120 s safety sweep. Now routed again.
- An oversized upgrade request got `400` instead of `431`.
- CI: semgrep flagged `std::env::args` in the Autobahn echo binary (it now reads environment
  variables); CodeQL flagged fixed nonces in auth unit tests (they now use random nonces; the
  published vector keeps its fixed nonce under the owner-approved `tests/` waiver, D-0015).

## Open risks and follow-ups

1. **The single-thread ceiling is the kernel.** At ~73k end-to-end messages/s CPU 0 is 100 %
   busy, over 80 % of it in syscalls and loopback softirq. Milestone 3 (thread-per-core,
   `SO_REUSEPORT`) and fewer syscalls per message are the levers.
2. **Stand-ins.** The in-memory mailbox and the in-process router each take a `Mutex` per
   operation (8 % of user CPU), which the constitution forbids on the hot path; they go away in M2
   and M3 (D-0021). Nothing here is durable, and the static device directory is refused outside
   development and CI, so `delivery` is not deployable until M2 and Prompt 3. The Ansible service
   template has no `[delivery]` section yet.
3. **TLS must end at `delivery`** (channel binding, D-0024): no TLS-terminating load balancer in
   front. The censorship proxy is unaffected (it forwards inner TLS untouched).
4. **One envelope copy per delivery** (header plus envelope in one WebSocket message). M3 removes
   it with a vectored header segment.
5. **Supply chain.** 22 new cargo-vet exemptions; sockudo-ws (parses every client byte, `unsafe`
   SIMD) and quanta are the ones to audit first (D-0017).
6. **Flamegraph has no kernel stacks** (`perf_event_paranoid=2` without root).
7. Not yet built (later milestones): SurrealDB mailbox and group commit, batched ACK deletes,
   device lists and MLS ordering (M2); runtime, per-core resources, zero allocation (M3); Valkey
   routing (M4); push jobs for offline devices (M5); restore and resend (M6).
