## The load suite (one command)

`bench/m7/suite.sh <work dir> [baseline.json]` builds the node and runs every scenario. It
prints the comparison against the stored baseline and fails on any tracked figure more than 10%
worse, or on a missed target. `bench/m7/baseline-vmpal-arm64.json` is this host's baseline.

| Scenario | Result (VM, 30,000 TLS devices unless noted) |
| --- | --- |
| Idle | **32.5 KiB per connection** (1.08 GB resident for 30,000). Connecting all of them took 43 s, paced by the per-core accept limits and TLS handshakes. |
| Steady, 1,000/s | Store p99 ≤2 ms. Client p50 0.88 ms, p99 2.3 ms, p99.9 5.0 ms. Delivery used about a third of one core. |
| Group, 20 sends/s × 255 recipients | 7,509 deliveries/s. Client p50 4.3 ms, p99 10.0 ms. Store p99 ≤10 ms: a shared body for 255 devices writes to every partition. |
| Storm | 15.5 s to full recovery; zero loss. |
| Max (8,000 devices) | **80,000 messages/s** sustained, client p99 3.4 ms, store p99 ≤3 ms, delivery on 3.5 of its 6 cores. The load generator's 4 cores, not delivery, set this ceiling: the true maximum is higher. |

CPU per message: about 330 µs of server CPU per message at 1,000/s, and 45 µs at 80,000/s. At
low rates each message pays its own cross-thread hand-offs (see the flamegraph). At the beta's
peak that is a third of one of eight cores, so it is not worth a redesign.

## What changed

- **ACK checkpoints no longer delay stores** (`crates/mailbox`).
  - Every 50 ms each partition's writer wrote pending ACKs as an append of its own. Under traffic
    there nearly always were some: about 20 extra Iggy writes per second per partition.
  - A store arriving during one waited an extra round trip: about 1.6% of sends, which set the p99.
  - ACKs already ride in every store batch's append. Now the tick writes them only when no batch
    has carried them for a whole interval (an idle partition).
  - Result: store p99 at the beta's peak went from ≤3 ms to ≤2 ms, and at 80,000/s from ≤5 ms to
    ≤3 ms.
  - Iggy live tests 16/16 and the e2e invariants pass.
- **Measurement in delivery:**
  - `songbird_delivery_store_seconds`: a lock-free per-core histogram (`ShardedHistogram`, fixed
    buckets from 50 µs to 1 s, no allocation).
  - Process figures in every service's metrics: `songbird_process_resident_memory_bytes`,
    `_cpu_seconds_total` and `_open_fds`, read from `/proc` at scrape time.
- **Load generator:**
  - scenarios `idle`, `storm` (with recovery time) and `group` (shared bodies, `--group-size`);
  - `--tls-ca` (TLS 1.3, a session cache per device);
  - `--admin`: memory per connection, CPU per 10,000 deliveries, and server store-latency
    quantiles between scrapes;
  - `--json-out`.
- **Scripts:**
  - `bench/m7/suite.sh`;
  - `bench/m7/profile.sh` (perf, inferno flamegraphs);
  - `bench/m7/soak.sh` (24 h, a per-minute sampler of memory, descriptors, CPU, store latency and
    Iggy's memory).
- `--features system-allocator` (benchmark only, off by default) to compare allocators.

## Threat model

§3.5.1 adds four rows:

- memory exhaustion by idle connections (33 KiB each against the 100,000 cap);
- reconnect storms;
- TLS resumption and session linking;
- a benchmark build reaching production.

## Open risks

1. **No 24-hour soak yet** (gate table). Slow leaks and drift are untested beyond a 150-second
   run.
2. **Durable latency and x86 unmeasured:** everything here ran on an arm64 VM with Iggy's data in
   memory. Production's store latency adds the server's NVMe fsync. The go-live check is
   `bench/m7/suite.sh` on the `ccx33`, with Iggy on its disk.
3. **Maximum throughput not found:** the load generator needs more cores (a second machine) to
   push delivery to saturation.
4. **The histogram's resolution** around the target is 1 ms (buckets at 1, 2 and 3 ms). "p99
   ≤2 ms" means the p99 is between 1 and 2 ms.
5. **CI keeps only the deterministic gates** (allocations, the checker). The timing comparison
   needs a fixed, quiet machine, so it runs where the suite runs.
