## Valkey compatibility (the prompt asked to verify it)

Two LiveKit `v1.13.11` nodes on one Valkey `9.1.3` (the pinned image), podman on Windows 11:
both start with Redis routing and register under `nodes`; a room `api` creates through node A is
joined through node B (LiveKit routes the signalling), node A lists the participant, and node A's
`RemoveParticipant` disconnects it on node B. The whole `gate_p07` suite also passes against this
cluster (7 of 7). **Valkey is compatible**; D-0085 §4 still gives LiveKit a dedicated instance.

## The harness (the gate's E2EE item)

`calls-harness ws://127.0.0.1:47880 http://127.0.0.1:47880 devkey <secret>`, LiveKit `v1.13.11`
in podman with `rtc.node_ip` set to the podman VM's address, Windows 11, Ryzen 9 7950X:

```text
PASS connect: Bob decodes Alice's end-to-end encrypted video
PASS connect: the SFU lists Alice's track as AES-GCM encrypted
PASS wrong key: Mallory, subscribed to Alice's video (1 track), decodes no frame of it (states seen: [])
PASS rotation: at epoch 1 (key index 1) Bob and Carol decode Alice
PASS rotation: after the removal (epoch 2, index 2) Bob still decodes (121 frames in 8 s)
PASS rotation: Carol, removed but still connected, decodes nothing (0 frames; states seen: [Ok, MissingKey])
calls-harness: all checks passed
```

- Tickets come from `songbird-calls` as `api` issues them: per-room pseudonyms, least grants,
  rooms created with caps.
- 1:1 keys come from a `call_secret` through `EpochSecret::one_to_one`; group keys from a real
  OpenMLS group's exporter (X-Wing suite, the `songbird-groups-harness` devices), and the removal
  is a real MLS commit.
- Carol was left connected to the SFU on purpose: the crypto alone cuts her off. In production
  `api` also disconnects her (M2).
- Media is synthetic video (flat frames of a known brightness), so a decoded frame proves the key
  was right; audio and data packets use the same keys and cryptor and are not separately checked.

## Decisions (D-0089)

- **TURN/TLS on the second address, signalling on the first**, both 443; LiveKit's
  `turn.bind_addresses` (read in the `v1.13.11` source) binds TURN's TLS and UDP listeners to the
  second address only. `turn_domain` must resolve to it.
- **One LiveKit Valkey per calls cluster, on the first calls host**, over mutual TLS (LiveKit's
  `redis.tls`, from `livekit/protocol`'s `xtls.Config`), no persistence: it holds routing only.
- **Signalling beside the edge role (beta's single host) moves to 8443**, since delivery and api
  hold 443 there. Production's calls hosts use 443.
- **The harness lives outside the workspace** with its own lock file and `+crt-static`; it is not
  in CI (libwebrtc download and build), and runs before a release, like the load tests.

## Changes from the plan

- The tofu change adds a floating IP rather than a second primary IP (Hetzner attaches one
  primary IPv4 per server); Ansible puts it on `eth0`.
- `deploy/` cannot be validated on this machine (no `tofu` or `ansible-lint`): CI's `validate-iac`
  checks it.

## Open risks

- **Not deployed**: certificates for `calls_domain` and `turn_domain` (public CA), DNS, and the
  `[api.calls]` and `[calls]` sections of the service configuration files (the templates still
  write `[common]` only, as for every service) are deployment work, with the owner's domain
  choice (D-0046).
- If the first calls host is lost, LiveKit's Valkey goes with it (routing only; rooms on other
  hosts keep running; the runbook restarts it elsewhere).
