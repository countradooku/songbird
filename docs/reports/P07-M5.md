# P07-M5 — Load, bandwidth per mode, loss and latency, and a sizing table

- Date: 2026-11-17
- Plan: [P07-plan.md](P07-plan.md) (D-0085); decision D-0090
- Status: measured; **approved by the owner on 2026-11-17** with the Prompt 7 gate (`P07-gate.md`).

## Setup

- **SFU:** LiveKit `v1.13.11` (pinned digest), one node, in podman (WSL 2) on Windows 11 Pro
  10.0.26300, Ryzen 9 7950X. The container is capped at **4 CPUs and 8 GB** (`--cpus 4 --memory
  8g`) to stand for one 4-vCPU calls host; `auto_create: false`, rooms created first.
- **Load:** LiveKit's load tester, `lk perf load-test` from `livekit-cli` **v2.19.2** (released
  2026-10-22; SHA-256 of `lk_2.19.2_windows_amd64.zip` checked against the release's
  `checksums.txt`), on the same machine, outside the CPU cap. Simulated publishers send prerecorded
  H.264/VP8 video (simulcast unless noted) or Opus; subscribers receive without decoding.
- **Measured:** subscriber bitrate and packet loss from `lk`'s summary; the SFU's CPU from its
  cgroup (`cpu.stat` `usage_usec`, sampled every 5 s, cores = CPU time over wall time, mean of the
  steady middle samples); peak memory from `memory.current`. 60 s per run, one run at a time.
- **Scripts:** `run.sh`, `rooms.sh`, `cpu.js` kept with the raw outputs in the session scratchpad;
  the commands are below so anyone can repeat them.

Notes:

- In C and D the testers subscribed to 75 % of the tracks (144 of 192, 720 of 960): `lk`'s
  default "speaker" layout and the testers' own limits on one machine. The cores are for the
  tracks actually forwarded.
- F–H: `tc netem` on the SFU's egress (a sidecar container in LiveKit's network namespace), so
  loss hits what the SFU sends and the RTCP it returns. Video recovered by NACK and retransmission
  and backed off its bitrate; audio by RED. The prompt's `tc netem` item is met in this form; loss
  on the publishers' uplink was not modelled.
- **Bandwidth per mode** (the WhatsApp-parity item): one HD camera costs a receiver 0.6–0.9 Mbit/s
  (simulcast, the layer the receiver's layout asks for); in low-data mode 0.15 Mbit/s, about **4×
  less**; a voice about 18–20 kbit/s. The SFU's CPU halves in low-data mode.
- E2EE adds nothing to the SFU: it forwards encrypted payloads it never opens (M4's harness ran
  with E2EE through the same LiveKit).

## Sizing table (per 4-vCPU calls host)

Planned at **70 % of 4 cores (2.8 cores)** and **700 Mbit/s** of egress, scaling the runs above
linearly. A Hetzner cloud host's network, not its CPU, is the first limit for video.

| Workload | Per call or room (SFU egress, cores) | Concurrent per host | Limited by |
| --- | --- | --- | --- |
| 1:1 video, normal | ≈ 3.7 Mbit/s, 0.017 cores | **≈ 170** calls | CPU (170) and bandwidth (190) |
| 1:1 video, low-data | ≈ 0.6 Mbit/s, ≈ 0.008 cores | **≈ 350** calls | CPU |
| 1:1 audio | ≈ 0.04 Mbit/s, ≈ 0.003 cores | **≈ 900** calls | CPU |
| Group video, 32 people (8 cameras) | ≈ 71 Mbit/s, 0.29 cores | **≈ 9** rooms (≈ 290 people) | CPU and bandwidth |
| Group audio, 128 people | ≈ 13 Mbit/s, 1.07 cores | **≈ 2** rooms (≈ 260 people) | CPU |

For the beta (D-0043's load profile: thousands of users), one calls host covers peaks of a
hundred-plus simultaneous video calls; two hosts give headroom and survive one loss.

## Caveats

- One machine plays SFU and testers; WSL's network path is not a data centre's. Re-run on the
  `calls` host class before production (`lk perf load-test` from a separate host), and replace
  this table with those numbers.
- Linear scaling is an assumption above the measured points (largest: 80 testers in 20 rooms;
  128 in one room).
- Simulated publishers do not adapt like real apps in poor networks; the harness (M4) is the
  check on real clients.

## Commands

```bash
lk room create --empty-timeout 300 <room>
lk perf load-test --room <room> --duration 60s --num-per-second 10 \
   --video-publishers 4 --subscribers 12 [--video-resolution low --no-simulcast]
lk perf load-test ... --audio-publishers 8 --subscribers 120
# netem on the SFU's egress, from a sidecar in its network namespace:
podman run -d --name netem --network container:sb7-livekit --cap-add NET_ADMIN alpine:3.22 sleep 3600
podman exec netem sh -c 'apk add iproute2-tc; tc qdisc add dev eth0 root netem delay 40ms 10ms loss 3%'
```
