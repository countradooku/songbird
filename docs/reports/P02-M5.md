## What was built

- **`crates/jobs`:** the job queue on Valkey Streams (`valkey-jobs`).
  - Jobs carry IDs only and **are sealed** (AES-256-GCM-SIV under the jobs secret, bound to their stream), so the persisted queue is not a record of who was messaged and when.
  - Pipelined `XADD`; a finished job is acknowledged and deleted (`XACK` + `XDEL`).
  - Retries use full-jitter exponential backoff through a Lua-promoted delayed set, timed by Valkey's clock.
  - Stuck jobs are reclaimed with `XPENDING … IDLE` + `XCLAIM`, which also gives a delivery cap for poison jobs.
  - A capped, sealed dead-letter stream.
  - An outbox relay and a consumer loop.
- **`crates/accounts`:** the account registry in SurrealDB.
  - Accounts, devices, a directory version, push tokens (stored under a keyed hash), upload grants, attachment records with no uploader, and the outbox.
  - A SurrealDB handle that reconnects.
  - **Push registrations sealed to the push service's X25519 key**, bound to their row. `api` and `worker` hold only the public key.
- **Mailbox `Forget`:** a new log record (sealed format 4; format 3 is still read).
  - It acknowledges the devices' pending entries (their keys are punctured) and drops their counters.
  - Replay applies it, so a restart or a standby's takeover keeps nothing of the devices.
  - Routed to the partition owner over node links.
- **Delivery:**
  - The directory loads from the registry and reloads when its version changes (`arc-swap`: readers take no lock).
  - An offline route queues a push job: a non-blocking hand-off, a per-device debounce, and pipelined batches.
  - `[delivery.internal]`: a mutual-TLS link that accepts only `worker.` certificates and only Forget/Known.
  - `Router::close_everywhere` closes a device's session on whichever node holds it.
- **`crates/push-providers` and `services/push`:**
  - APNs (HTTP/2, ES256 provider token, a separate VoIP path), FCM HTTP v1 (OAuth service account), and UnifiedPush/Web Push (RFC 8291 encryption, RFC 8292 VAPID, an SSRF guard).
  - Every push is identical: a constant alert text, empty FCM data, a constant encrypted body, constant collapse IDs.
  - A circuit breaker per provider, HTTP/2 connection pools, and mock servers for tests.
  - Provider credentials exist only in the push service's configuration.
- **`crates/s3`:** our own SigV4 client for RustFS over hyper (no AWS SDK), checked against AWS's published vectors.
- **`services/api`:**
  - No tokens: every request is **signed with the device's key**, with single-use nonces.
  - Push registration.
  - Attachment grants with an exact size, uploads streamed through `api` to RustFS (RustFS is never exposed), and downloads that count fetches, the last one queuing deletion.
  - `DELETE /v1/account` through the outbox.
  - An admin link (`admin.` certificates only) to create accounts until Prompt 3.
- **`services/worker`:**
  - Account deletion, each step idempotent: forget, delete push tokens, grants and objects, forget again after the directory has propagated, verify, delete rows, verify again.
  - Attachment cleanup.
  - Sweeps for 30-day-old attachments, fully fetched ones and expired grants.
  - The outbox relay.
- **Docs:** the threat model (two approved rows, two awaiting approval, §3.6 with 11 threats), the runbook `jobs-push-api-worker.md`, D-0036 with its implementation and evidence, and dev config examples.
- **CI:** the compose job runs every new live test and the gate.

## Open risks

1. **The Iggy path is not run on this machine;** the CI compose job must pass it.
2. **No real push providers tested.** Mocks only. Not yet verified with Apple, Google or UnifiedPush distributors:
   - whether FCM wakes an app with a message that has no `data` field;
   - Apple's handling of the VoIP `{}` payload.
3. **One RustFS credential in development.** Per-service least-privilege users and bucket policies (D-0035) are a deployment task, not automated yet.
4. **A deleted device can authenticate until the next directory reload** (1 s), longer if SurrealDB is unreachable then. Its open sessions are closed at once by the deletion.
5. **Download counting is per completed download, not per recipient** (recording recipients would link them to the object). A device that downloads twice uses two fetches; the 30-day expiry bounds the cost.
6. **Account creation is a stand-in:** the admin link, until Prompt 3's registration.
7. **Backups (M6)** are not part of this deletion; their retention is M6's.
8. **CI isolation:** the stream-sharing live tests run one at a time in CI because they share fixed stream names. A queue namespace would let them run in parallel.
