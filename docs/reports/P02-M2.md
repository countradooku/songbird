## Numbers

### Per-statement cost (`crates/surreal/examples/rtt.rs`, p50 / p99)

| Request | In-memory engine | SurrealKV, `sync=every` |
| --- | --- | --- |
| RPC ping | 25 / 267 µs | 25 / 53 µs |
| `RETURN 1` | 127 / 239 µs | 123 / 198 µs |
| `BEGIN; RETURN 1; COMMIT` | 140 / 254 µs | 133 / 254 µs |
| Create one row | 362 / 1,379 µs | 906 / 1,809 µs |
| Same in a transaction | 361 / 477 µs | 942 / 1,546 µs |

SurrealQL execution costs 0.1–1.5 ms per statement; a durable one-row write is 0.9 ms.

### Store throughput (`commit_bench`, final design, `max_wait` 0, one recipient per send)

Each sender waits for its send's answer before the next one; a commit is one fsynced transaction.

| Senders | Sends/s | Commits/s | Sends per commit | p50 | p99 | p99.9 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 303 | 303 | 1 | 3.3 ms | 4.1 ms | 4.8 ms |
| 16 | 3,781 | 236 | 16 | 4.2 ms | 5.8 ms | 7.3 ms |
| 128 | 11,557 | 90 | 128 | 10.8 ms | 15.1 ms | 17.9 ms |
| 1,024 | 12,572 | 49 | 256 | 75.0 ms | 451 ms | 455 ms |

Group fan-out with shared bodies: 64 senders to 100-device groups 22,005 mailbox entries/s; 16
senders to 1,000-device groups 20,455 entries/s (about 45 µs per entry). One 1,000-device shared
send alone takes 51 ms (554 ms with the first design).

How we got here (same benchmark, `max_wait` 1 ms):

| Design | 1 sender | 128 senders | 1,024 senders |
| --- | --- | --- | --- |
| First: one transaction with `FOR` loops and closures computing `seq`s in SurrealQL | 129/s, 7.7 ms | 3,900/s | 3,393/s |
| Cached counters, bulk statements, compare-and-set guard (durable) | 228/s, 4.4 ms | 10,473/s | 14,130/s |
| Same, in-memory engine | 253/s, 3.9 ms | 11,831/s | 16,806/s |
| Final, `max_wait` 0 (durable) | 303/s, 3.3 ms | 11,557/s | 12,572/s |

The in-memory engine is only about 10–20 % faster than the durable one: SurrealDB's execution, not
fsync, sets the ceiling.

### Delivery end to end on SurrealDB (load generator, checker)

1,000 devices, 1:1 random traffic, 256-byte envelopes, `delivery` one thread, store in SurrealKV
with `sync=every`. Each message is a store transaction share, a delivery and an ACK delete share,
all through the one writer.

| Offered | Achieved | p50 | p99 | p99.9 | max | Checker |
| --- | --- | --- | --- | --- | --- | --- |
| 1,000/s ¹ | 1,000/s | 4.6 ms | 13.9 ms | 19.0 ms | 23.0 ms | pass |
| 5,000/s | 4,996/s | 11.6 ms | 33.4 ms | 39.3 ms | 49.8 ms | pass |
| 10,000/s | 7,136/s (saturated) | 209 ms | 299 ms | 305 ms | 408 ms | pass |
| 15,000/s | 7,157/s (saturated) | 209 ms | 304 ms | 362 ms | 385 ms | pass |

¹ From the run before the ACK-starvation fix (below), which only changes behaviour at saturation.

Against M1's in-memory stand-in (73,000 messages/s on one core) the store now costs ten times the
whole rest of the path: the node's ceiling is about 7,150 messages/s, set by SurrealDB.

### Degraded modes

- **Reconnect chaos**: 3,000/s for 20 s, a random connection dropped every 20 ms and all 1,000 at
  once at 10 s: 59,992 accepted, 820 retried sends, 1,950 aborts, **0 lost, 0 duplicates, 0 order
  violations**; p50 6.0 ms, p99 45 ms, max 183 ms.
- **SurrealDB paused for 8 s** (`podman pause`) in a 20 s run at 2,000/s: sends stall for the
  pause and resume; 24,888 accepted, 0 rejected, **0 lost, 0 duplicates, 0 order violations**;
  max latency 8.13 s (the pause). No socket was closed.

## Bugs found and fixed during the milestone

- Store and ACK transactions both wrote the per-device counter record and aborted each other on
  SurrealDB's optimistic conflict check (55 s for a 1-second test). Separate `ackctr` records, then
  a single writer: 1.0 s.
- Under saturation the writer's send-biased loop starved ACK flushes; the queue then dropped ACKs,
  entries were never deleted and a later run hit the capacity limit (10,000 sends rejected).
  Queued ACKs are now taken on every wake-up; re-run passes.
- Shared-body reference counts were decremented in a separate transaction from the entry delete
  (a 1,000-device test saw 1,000 references left). Now one transaction.
- `SCHEMAFULL` tables refuse unknown fields: the compare-and-set `prev` field is defined.
- Parallel test start raced the schema definition: connect retries it for about 10 s.

## Open risks and follow-ups

1. **SurrealDB sets the ceiling**: about 7,150 messages/s end to end and 3.3 ms per lone send on
   this machine, against Prompt 2's p99 targets of a few milliseconds. M3 tries several writers
   per node sharded by device; TiKV (the later cluster) changes every number. This needs the
   owner's view before M3 (below).
2. **Root credentials** to SurrealDB; least privilege is Prompt 12's.
3. **Static device directory** still; the identity service (Prompt 3) owns devices, accounts and
   key versions (`DeviceMismatch.stale` stays empty until then). `delivery` stays not deployable.
4. **MLS commit authorization** (who may commit to a group) is Prompt 5's; until then any
   authenticated device can advance a group's epoch it knows the ID of.
5. **One envelope copy per delivery** and the stand-in router's mutex remain (M3).
6. Not yet built: runtime, per-core resources, zero allocation (M3); Valkey routing (M4); push
   for offline devices (M5); restore and resend (M6).
